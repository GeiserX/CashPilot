# अक्सर पूछे जाने वाले प्रश्न { #faq }

**क्या बैंडविड्थ साझा करना सुरक्षित है?**

बैंडविड्थ साझा करने वाली सेवाएँ आम तौर पर वैध ट्रैफ़िक (बाज़ार अनुसंधान, विज्ञापन सत्यापन, कीमतों की तुलना, कंटेंट डिलीवरी) आपके कनेक्शन से भेजती हैं। फिर भी, आप अपना IP पता साझा कर रहे हैं, इसलिए साइन अप करने से पहले हर सेवा की सेवा शर्तें और गोपनीयता नीति ध्यान से पढ़ें। कुछ सेवाओं के लिए इन्हें आवासीय IP के बजाय VPS पर चलाना भी एक विकल्प है। **यह कानूनी सलाह नहीं है -- जिन सेवाओं को आप इस्तेमाल करना चाहते हैं उनसे पूछें और, ज़रूरत हो तो, अपने क्षेत्राधिकार के बारे में किसी स्वतंत्र कानूनी सलाहकार से सलाह लें।**

**मैं कितना कमा सकता हूँ?**

कमाई जगह, ISP, डिवाइस की संख्या और आपकी चलाई सेवाओं के हिसाब से बहुत बदलती है। डैशबोर्ड समय के साथ आपकी असली कमाई पर नज़र रखता है, ताकि आप अपना सेटअप बेहतर बना सकें। एक मोटे अंदाज़े के तौर पर, कोई वादा नहीं, 10 से 15 सेवाएँ चलाने वाला एक होम सर्वर महीने में लगभग $30 से $100 कमाता है, और यह कम भी कमा सकता है, शून्य तक। ज़्यादा सर्वर, या GPU कंप्यूट, इसमें और जोड़ते हैं।

**क्या मैं इसे VPS या क्लाउड सर्वर पर चला सकता हूँ?**

कुछ सेवाओं को आवासीय IP चाहिए और वे VPS/डेटा सेंटर IP को भुगतान नहीं करेंगी (या उन पर रोक लगा देंगी)। कैटलॉग उनकी ज़रूरतों में "residential IP" लिखता है। VPS पर काम करने वाली सेवाएँ घर में अतिरिक्त हार्डवेयर के बिना विस्तार करने का अच्छा तरीका हैं।

**क्रेडेंशियल कैसे रखे जाते हैं?**

सेवाओं के सभी क्रेडेंशियल SQLite डेटाबेस में `/data/.fernet_key` में रखी Fernet कुंजी से एन्क्रिप्ट करके रखे जाते हैं, जो पहली बार चलने पर अपने आप बनती है। डेटाबेस फ़ाइल माउंट किए गए Docker वॉल्यूम (`cashpilot_data:/data`) में रहती है। क्रेडेंशियल सेवा कंटेनरों के अलावा कभी कहीं नहीं भेजे जाते।

ध्यान दें कि यह `CASHPILOT_SECRET_KEY` से अलग कुंजी है, जो केवल लॉगिन सेशन पर हस्ताक्षर करती है।

### एन्क्रिप्शन कुंजी का बैकअप { #backing-up-the-encryption-key }

आपके क्रेडेंशियल उतने ही वापस पाने लायक हैं जितनी `/data/.fernet_key`। अगर वह फ़ाइल खो जाए, तो आपको हर क्रेडेंशियल फिर से डालना होगा, क्योंकि उसके बिना सहेजे गए मानों को डिक्रिप्ट करने का कोई तरीका नहीं है।

```bash
# Back it up
docker exec cashpilot-ui cat /data/.fernet_key

# Restore onto a fresh volume: pass the saved value when starting CashPilot.
# It must reach the container, so put it on the same command line (or export it,
# or set it in your .env) - a bare shell assignment on its own line does nothing.
CASHPILOT_ENCRYPTION_KEY=<the value you saved> docker compose up -d
```

फ़ाइल हमेशा एनवायरनमेंट वेरिएबल से ऊपर रहती है, इसलिए जिस इंस्टेंस के पास पहले से कुंजी है उस पर `CASHPILOT_ENCRYPTION_KEY` सेट करने से कुछ नहीं बदलता और यह सुरक्षित है। इसे केवल तब अपनाया जाता है जब कोई कुंजी फ़ाइल न हो, और ठीक यही पुनर्स्थापना की स्थिति है।

अगर CashPilot कुंजी को डिस्क पर लिख ही नहीं पाता, क्योंकि `/data` पर लिखा नहीं जा सकता या वह माउंट नहीं है, तो वह आपके क्रेडेंशियल को ऐसी कुंजी से एन्क्रिप्ट करने के बजाय शुरू होने से मना कर देता है जो अगले restart पर गायब हो जाए। अगर आप सच में यही चाहते हैं, तो `CASHPILOT_ALLOW_EPHEMERAL_KEY=true` सेट करें।

<a id="forgot-password"></a>

### पासवर्ड या यूज़रनेम भूल गए { #forgot-password-or-username }

CashPilot में ई-मेल से reset नहीं होता। जो व्यक्ति सर्वर चलाता है, वह CashPilot UI कंटेनर के console से पासवर्ड reset करता है। आपकी सेवाओं, कमाई और सहेजे गए क्रेडेंशियल पर कोई असर नहीं पड़ता: वे `/data/.fernet_key` से एन्क्रिप्ट होते हैं, आपके पासवर्ड से नहीं।

`python -m app.users` कमांड के लिए CashPilot 2.3 या नया चाहिए। 2.2 या पुराने पर यह `No module named app.users` के साथ विफल होता है। पहले अपडेट करें: Docker Compose के साथ `drumsergio/cashpilot` और `drumsergio/cashpilot-worker` टैग को `2.3` या नए पर बदलें (`2.2` या `2.2.9` जैसा पिन उसी रिलीज़ पर रहता है), फिर `docker compose up -d` चलाएँ ([CashPilot अपडेट करना](getting-started.md#updating-cashpilot))। Unraid पर कंटेनर अपडेट करें।

1. खातों की सूची देखें। इससे भूला हुआ यूज़रनेम भी दिख जाता है। यूज़रनेम में छोटे-बड़े अक्षरों का फ़र्क पड़ता है।

    ```bash
    docker exec -it cashpilot-ui python -m app.users list
    ```

2. खाते के लिए एक नया random पासवर्ड सेट करें। `alice` को चरण 1 के यूज़रनेम से बदलें।

    ```bash
    docker exec -it cashpilot-ui python -m app.users reset-password alice
    ```

    अगर ठीक एक ही स्वामी है, तो आप यूज़रनेम छोड़ सकते हैं, और कमांड उसी स्वामी का पासवर्ड reset करती है। अगर यूज़रनेम `-` से शुरू होता है, तो उससे पहले `--` लगाएँ: `reset-password -- -alice`।

    कमांड नया पासवर्ड एक बार दिखाती है।

3. अगर किसी और के पास खाते तक पहुँच रही हो सकती है, तो अभी UI कंटेनर को restart करें (`docker restart cashpilot-ui`)। जो ब्राउज़र अब भी उस उपयोगकर्ता के रूप में साइन इन थे, वे restart के बाद ही साइन आउट होते हैं। अगर आप केवल पासवर्ड भूल गए थे, तो restart वैकल्पिक है।
4. नए पासवर्ड से साइन इन करें, फिर उसे अवतार मेनू (ऊपर दाईं ओर) से, **Change password** (पासवर्ड बदलें) में बदलें।

कंटेनर का नाम इस पर निर्भर करता है कि आपने CashPilot कैसे इंस्टॉल किया:

| इंस्टॉल | UI कंटेनर |
|---|---|
| `docker-compose.yml`, CasaOS | `cashpilot-ui` |
| Unraid | `cashpilot` (`docker exec -it cashpilot python -m app.users list`) |
| Runtipi | एक बनाया गया नाम; `docker ps` उसे दिखाता है |

Portainer, Unraid और CasaOS में भी कंटेनर के लिए console बटन होता है। कमांड को terminal इनपुट की ज़रूरत नहीं होती, इसलिए यह वहाँ भी काम करती है।

यूज़रनेम बदलने के लिए:

```bash
docker exec -it cashpilot-ui python -m app.users rename OLD NEW
```

नया नाम पंजीकरण के नियम का पालन करता है: 3 से 32 अक्षर, अंक, `_` या `-`। इसे देखने के लिए साइन आउट करके फिर से साइन इन करें।

**किसी सेंध के शक के बाद**, जैसे `/data/.secret_key` वाला कोई बैकअप खो जाने पर, केवल पासवर्ड reset काफ़ी नहीं है। जिसके पास वह कुंजी है, वह एक मान्य लॉगिन cookie पर हस्ताक्षर कर सकता है, और reset उसे नहीं रोकता। कुंजी बदलें, फिर UI कंटेनर को restart करें। `&&` उसे केवल तभी restart करता है जब नई कुंजी अपनी जगह पर हो; अगर कमांड कोई error दिखाए, तो पहले उसे ठीक करें:

```bash
docker exec cashpilot-ui python -m app.users rotate-session-key && docker restart cashpilot-ui
```

restart के बाद हर ब्राउज़र साइन आउट हो जाता है, और सब लोग अपने पासवर्ड से फिर से साइन इन करते हैं। सहेजे गए क्रेडेंशियल पर कोई असर नहीं पड़ता। अगर आपने `CASHPILOT_SECRET_KEY` खुद सेट की है, तो कमांड मना कर देती है: इसके बजाय उस वेरिएबल में एक नया random मान डालें और कंटेनर को फिर से बनाएँ। इमेज से किया गया `docker run` वह वेरिएबल नहीं देखता और मना नहीं कर सकता, इसलिए UI कंटेनर पर `docker exec` इस्तेमाल करें।

नई कुंजी नकली cookies को ख़त्म कर देती है, पर हमलावर ने अंदर रहते हुए जो किया उसे नहीं। दो और कदम:

1. `docker exec cashpilot-ui python -m app.users list` चलाएँ। जिस खाते को आप नहीं पहचानते, उसे डैशबोर्ड से हटा दें।
2. अगर खोई हुई कॉपी में पूरा `/data` था, तो अपने प्रदाता खातों के पासवर्ड बदलें। `.fernet_key` और `cashpilot.db` मिलकर हर सहेजे गए क्रेडेंशियल को डिक्रिप्ट कर देते हैं।

अगर आप बाद में rotation से पहले लिया गया कोई बैकअप पुनर्स्थापित करते हैं, तो उसकी `.secret_key` छोड़ दें ([बैकअप और पुनर्स्थापना](backup-restore.md#restore)), या फिर से rotate और restart करें। नहीं तो पुरानी कुंजी वापस आ जाती है। पुनर्स्थापित डेटाबेस उसमें रखे खाते और पासवर्ड भी वापस ले आता है, इसलिए खातों की जाँच और कोई भी पासवर्ड reset फिर से करें।

**अगर UI कंटेनर शुरू नहीं होता**, तो वही कमांड उसी इमेज से उसी डेटा पर चलाएँ। पहले होस्ट का वह फ़ोल्डर खोजें जिसमें UI का `/data` है। यह रुके हुए कंटेनर पर भी काम करता है, और named volume के साथ-साथ bind mount (Unraid, CasaOS, Runtipi) पर भी:

```bash
docker inspect -f '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}' cashpilot-ui
```

फिर उस फ़ोल्डर को माउंट करें और वही इमेज टैग इस्तेमाल करें जो आप चलाते हैं:

```bash
docker run --rm -v "<folder>:/data" --entrypoint python drumsergio/cashpilot:<same tag> -m app.users list
```

जाँचें कि सूची में आपके खाते दिख रहे हैं, फिर वही लाइन `list` की जगह `reset-password alice` के साथ चलाएँ।

जिस path पर कोई डेटाबेस नहीं है, वह "no database" error देता है, और कमांड वहाँ कुछ नहीं बनाती और कुछ नहीं बदलती। Docker फिर भी उस नाम का एक खाली फ़ोल्डर या वॉल्यूम पीछे छोड़ सकता है; उसे हटा दें।

डेटा वॉल्यूम **न** हटाएँ: इससे `/data/.fernet_key` मिट जाती है और उसके साथ हर सहेजा गया क्रेडेंशियल। `users` तालिका से पंक्तियाँ भी **न** हटाएँ।

**मैं CashPilot को पूरी तरह कैसे हटाऊँ?**

`docker compose down -v` केवल CashPilot के अपने कंटेनर हटाता है। इसकी डिप्लॉय की गई सेवाएँ चलती रहती हैं, और उनका डेटा, सुरक्षा घेरे वाला नेटवर्क और एक firewall तालिका बने रहते हैं। [CashPilot को पूरी तरह हटाना](uninstall.md) यह सब हटाता है, बताता है कि क्या हमेशा के लिए खो जाता है, और दिखाता है कि कुछ भी बचा नहीं है यह कैसे जाँचें।

**सुरक्षा का क्या?**

CashPilot जो भी सेवा डिप्लॉय करता है, वह अपने कंटेनर में चलती है, जिसमें हर Linux capability हटा दी जाती है (कुछ सेवाएँ केवल वही वापस जोड़ती हैं जो वे घोषित करती हैं) और `--security-opt no-new-privileges` सेट होता है, इसलिए अंदर का कोई process विशेषाधिकार नहीं पा सकता। कंटेनर किसी सेवा के घोषित वॉल्यूम से आगे आपके होस्ट का फ़ाइल सिस्टम नहीं देख सकते। नए इंस्टॉल पर वर्कर उन्हें आपके LAN, होस्ट, आपके tailnet और cloud metadata से घेरकर अलग भी करता है, इसलिए वे इंटरनेट तक पहुँचते हैं और किसी स्थानीय चीज़ तक नहीं ([नेटवर्क पृथक्करण](isolation.md))। Podman पर सुरक्षा घेरा उपलब्ध नहीं है: कमाई ऐप Podman के डिफ़ॉल्ट नेटवर्क पर चलते हैं, जो आपके LAN तक पहुँच सकता है, और फ़्लीट पेज यह बताता है ([नेटवर्क पृथक्करण](isolation.md) विकल्प बताता है)। 1.70 से पहले के रिलीज़ से अपग्रेड किया गया इंस्टॉल अपने कमाई ऐप Docker के डिफ़ॉल्ट bridge पर रखता है, जो आपके LAN तक पहुँच सकता है, जब तक आप फ़्लीट पेज पर **Turn on isolation** (पृथक्करण चालू करें) पर क्लिक नहीं करते। 2.0.7 से Mysterium भी सुरक्षा घेरे के पीछे चलता है; 2.0.6 तक डिप्लॉय किया गया नोड तब तक होस्ट के नेटवर्क पर रहता है जब तक आप उसे फिर से डिप्लॉय नहीं करते ([अपने Mysterium नोड को सुरक्षा घेरे के पीछे ले जाना](mysterium-fence.md))। [अपने घरेलू नेटवर्क की सुरक्षा](home-network-security.md) इसके बजाय अपने bridge पर firewall लगाने के बारे में बताता है। सेवाओं के क्रेडेंशियल Fernet symmetric एन्क्रिप्शन से स्टोरेज में एन्क्रिप्ट किए जाते हैं। UI के पास Docker तक कोई पहुँच नहीं है। साथ आने वाली compose फ़ाइलों के साथ वर्कर को कभी सीधा Docker socket नहीं दिया जाता: वह `cashpilot-socket-proxy` के ज़रिए Docker तक पहुँचता है, जो privileged कंटेनरों और `/` या socket के bind को मना करता है (जब तक आप उनमें से किसी को, या socket से ऊपर के किसी फ़ोल्डर को, `CASHPILOT_PROXY_BIND_MOUNTS` या `CASHPILOT_COMPOSE_DIR` में न डालें: proxy उन्हें जैसा दिया गया वैसा मान लेता है), और वर्कर को केवल उसके owner लेबल वाले कंटेनरों, वॉल्यूम और नेटवर्क तक सीमित रखता है ([सुरक्षा डिफ़ॉल्ट](security-defaults.md))। Unraid टेम्पलेट और TrueNAS ऐप अब भी वर्कर में सीधा socket माउंट करते हैं, जो होस्ट पर root के बराबर है ([ऐप स्टोर](app-stores.md))।

फिर भी, कोई भी सेटअप पूरी तरह अभेद्य नहीं है। आप अब भी ऐसा तीसरे पक्ष का सॉफ़्टवेयर चला रहे हैं जो बाहरी ट्रैफ़िक आपके नेटवर्क से भेजता है। इन सेवाओं को सीधे होस्ट पर चलाने की तुलना में Docker का पृथक्करण हमले की सतह को काफ़ी कम करता है, पर यह हर जोखिम ख़त्म नहीं करता। हम सलाह देते हैं कि CashPilot को किसी अलग मशीन या VLAN पर चलाएँ, Docker और होस्ट OS को अपडेट रखें, और किसी भी सेवा को डिप्लॉय करने से पहले उसका open-source कोड देखें।

**अगर कोई सेवा कंटेनर crash हो जाए तो क्या होता है?**

CashPilot लगातार कंटेनर की सेहत पर नज़र रखता है। अगर कोई सेवा कंटेनर अचानक बंद हो जाता है, तो उसे अपने आप फिर से शुरू किया जाता है। डैशबोर्ड हर चल रही सेवा का uptime और सेहत की स्थिति दिखाता है।

**फिर से डिप्लॉय करने के बाद मेरा Mysterium नोड शुरू नहीं होता। क्यों?**

सबसे आम कारण उसकी UDP सीमा का कोई पोर्ट है जिसे होस्ट पर कोई दूसरा प्रोग्राम पहले से पकड़े हुए है। Docker को सीमा का हर पोर्ट आरक्षित करना होता है, इसलिए एक व्यस्त पोर्ट भी शुरुआत रोक देता है। [UDP पोर्ट सीमा चुनना](mysterium-fence.md#choosing-the-udp-port-range) बताता है कि ऐसी सीमा कैसे चुनें जो खाली रहे।

**मेरी प्रॉक्सी कॉपी चल रही है पर कुछ नहीं कमाती। क्यों?**

हो सकता है प्रॉक्सी उस कमाई ऐप के सर्वरों से जुड़ने से मना करता हो, या केवल पोर्ट 80 और 443 की अनुमति देता हो। CashPilot का **Test** (परीक्षण) केवल यह जाँचता है कि प्रॉक्सी इंटरनेट तक पहुँचता है। [प्रॉक्सी के ज़रिए कमाई ऐप के सर्वर जाँचें](proxies.md#probe-an-earners-servers-through-the-proxy) दिखाता है कि कमाई ऐप का अपना होस्ट और पोर्ट कैसे जाँचें।

**कौन-सी सेवाएँ भारी हैं, और उन्हें कहाँ चलाना चाहिए?**

स्टोरेज नोड, रिले और VPN exits, और GPU का काम सबसे ज़्यादा संसाधन लेते हैं। [छोटी मशीन का बजट बनाना](fleet.md#budgeting-a-small-box) उन्हें सूचीबद्ध करता है और दिखाता है कि तय करने से पहले हर कंटेनर को कैसे मापें।

### Docker अपडेट के बाद वर्कर ने Docker खो दिया { #the-worker-lost-docker-after-a-docker-update }

**आपको क्या दिखता है।** वर्कर फ़्लीट पेज पर ऑनलाइन रहता है, पर CashPilot उसके कंटेनरों को शुरू, बंद या अपडेट नहीं कर पाता। फ़्लीट पेज वर्कर के बगल में **Docker unreachable** (Docker तक पहुँच नहीं) दिखाता है। 10 मिनट के बाद वर्कर का healthcheck विफल होता है (`docker ps` वर्कर को `unhealthy` दिखाता है)। 30 मिनट के बाद घंटी और आपकी सूचनाएँ बताती हैं कि वर्कर Docker तक नहीं पहुँच पा रहा। `docker logs cashpilot-socket-proxy` में `upstream Docker socket unreachable` दिखता है, और मौजूदा compose फ़ाइल के साथ `docker ps` लगभग 3 मिनट के भीतर proxy को `unhealthy` दिखाता है। आपके कमाई ऐप चलते रहते हैं।

**कारण।** साथ आने वाली compose फ़ाइलें socket फ़ाइल `/var/run/docker.sock` को `cashpilot-socket-proxy` में bind करती हैं। फ़ाइल bind उसी एक फ़ाइल को पकड़े रखता है। Docker अपडेट (जैसे `unattended-upgrades` का नया `docker-ce` इंस्टॉल करना) Docker को restart करता है, और Docker उसी path पर एक नई socket फ़ाइल बनाता है। Docker का live-restore चालू हो, तो proxy उस restart के दौरान चलता रहता है और पुरानी फ़ाइल रखे रहता है। पुरानी फ़ाइल पर कोई जवाब नहीं देता।

**तुरंत समाधान।** उस मशीन पर proxy को restart करें:

```bash
docker restart cashpilot-socket-proxy
```

restart नए socket को bind करता है, और वर्कर अपनी अगली हार्टबीट पर फिर से Docker पा लेता है। आपको वर्कर को restart करने की ज़रूरत नहीं है। Unraid और TrueNAS पर वर्कर खुद socket रखता है, इसलिए वर्कर को restart करें।

**स्थायी समाधान।** socket फ़ाइल के बजाय socket का फ़ोल्डर bind करें। फ़ोल्डर bind बदला गया socket तुरंत दिखा देता है। अपनी compose फ़ाइल की `cashpilot-socket-proxy` सेवा में `- /var/run/docker.sock:/var/run/docker.sock:ro` लाइन को नीचे दिए bind से बदलें, और उसके `environment` में `SOCKGUARD_UPSTREAM_SOCKET` लाइन जोड़ें:

```yaml
    volumes:
      - type: bind
        source: /var/run
        target: /host-run
        read_only: true
        bind:
          recursive: disabled
      - cashpilot_docker_api:/run/cashpilot-docker
    environment:
      # Keep the lines that are already there, and add this one:
      - SOCKGUARD_UPSTREAM_SOCKET=/host-run/docker.sock
```

फिर `docker compose up -d` चलाएँ। यही बदलाव `docker-compose.worker.yml` और `docker-compose.fleet.yml` में भी काम करता है। Compose इन फ़ाइलों को केवल तब पढ़ता है जब आप उनका नाम देते हैं, इसलिए `docker compose -f docker-compose.worker.yml up -d` या `docker compose -f docker-compose.fleet.yml up -d` चलाएँ, जब तक `COMPOSE_FILE` पहले से फ़ाइल का नाम न देता हो।

- `recursive: disabled` ज़रूरी है। `/var/run` में दूसरे mounts भी होते हैं, जैसे `/run/docker/netns` के नीचे Docker के network namespaces और `/run/user/...`। recursive bind उन सबको proxy में ले आता है। non-recursive bind केवल फ़ोल्डर को ही दिखाता है।
- `SOCKGUARD_UPSTREAM_SOCKET` proxy को नए path पर भेजता है। policy ब्लॉक और उसका fingerprint जैसे हैं वैसे रहते हैं, क्योंकि एनवायरनमेंट वेरिएबल policy में `upstream.socket` को override करता है। वेरिएबल के बिना proxy शुरू नहीं होता (`upstream socket not found (/var/run/docker.sock)`)।
- `cashpilot-migrate` अपना फ़ाइल bind रख सकता है। यह हर `docker compose up` पर फिर से शुरू होता है, इसलिए इसे हमेशा मौजूदा socket मिलता है। अगर आप इसे वही फ़ोल्डर bind देते हैं, तो इसके `environment` में `DOCKER_HOST=unix:///host-run/docker.sock` जोड़ें। Worker 2.8.4 और नए संस्करण वह वेरिएबल पढ़ते हैं। इसे कभी proxy के socket पर न भेजें: migrator को होस्ट का अपना socket चाहिए।
- फ़ोल्डर bind proxy को `/var/run` का हर socket देता है, केवल Docker का नहीं। एक आम सर्वर पर इसमें systemd का अपना socket, D-Bus, और Tailscale या snapd जैसे टूल के sockets आते हैं। `read_only` किसी प्रोग्राम को socket से जुड़ने से नहीं रोकता, और proxy root के रूप में चलता है। Docker socket तक पहुँच पहले से होस्ट पर root देती है, इसलिए सेंध लगा proxy ऐसा बहुत कम पाता है जो उसके पास पहले से नहीं था। अगर आप चाहते हैं कि proxy केवल Docker socket रखे, तो फ़ाइल bind रखें और Docker अपडेट के बाद proxy को restart करें: ऊपर का अलर्ट आपको बताता है कि कब।
- इसके लिए Docker Compose 2.30.0 या नया चाहिए। पुराने रिलीज़ `Additional property recursive is not allowed` के साथ पूरी फ़ाइल को मना कर देते हैं। जाँचने के लिए `docker compose version` चलाएँ। Debian 13 में Compose 2.26.1 पैकेज है, इसलिए Debian पर Compose को Docker की अपनी रिपॉज़िटरी से इंस्टॉल करें। ऐप के अंदर का अपडेट अपना Compose 2.33 इस्तेमाल करता है, इसलिए वह बदली हुई फ़ाइल पढ़ लेता है।
- यह केवल Linux पर काम करता है। macOS और Windows पर Docker Desktop अपनी virtual machine में केवल `/var/run/docker.sock` को मैप करता है। वहाँ `/var/run` आपके Mac या PC का एक फ़ोल्डर है, जिसमें कोई Docker socket नहीं होता।
- rootless Docker के साथ socket `/run/user/<your uid>` में होता है, जो एक अलग mount है। उसी फ़ोल्डर को `source` के रूप में इस्तेमाल करें।
- Podman पर फ़ाइल bind रखें। हमने वहाँ फ़ोल्डर bind का परीक्षण नहीं किया है।

साथ आने वाली फ़ाइलें फ़ाइल bind रखती हैं, क्योंकि फ़ोल्डर bind के लिए Compose 2.30 और Linux चाहिए, और CashPilot पुराने Compose रिलीज़ और Docker Desktop का भी समर्थन करता है। आप जो नई compose फ़ाइल डाउनलोड करते हैं उसमें आपका बदलाव नहीं होता, इसलिए फ़ाइल बदलने के बाद यह बदलाव फिर से करें।

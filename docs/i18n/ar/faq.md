# الأسئلة الشائعة { #faq }

**هل مشاركة عرض النطاق آمنة؟**

توجّه خدمات مشاركة عرض النطاق عمومًا حركة مرور مشروعة (أبحاث السوق، والتحقق من الإعلانات، ومقارنة الأسعار، وتوصيل المحتوى) عبر اتصالك. ومع ذلك، فأنت تشارك عنوان IP الخاص بك، لذلك راجع شروط الخدمة وسياسة الخصوصية لكل خدمة بعناية قبل التسجيل. وتشغيل هذه الخدمات على VPS بدلًا من عنوان IP منزلي خيار متاح لبعض الخدمات. **هذه ليست استشارة قانونية -- راجع الخدمات المحددة التي تنوي استخدامها، واطلب عند الحاجة استشارة قانونية مستقلة بشأن الولاية القضائية التي تخضع لها.**

**كم يمكنني أن أكسب؟**

تختلف الأرباح كثيرًا حسب الموقع، ومزوّد خدمة الإنترنت، وعدد الأجهزة، والخدمات التي تشغّلها. تتتبّع لوحة التحكم أرباحك الفعلية بمرور الوقت حتى تستطيع تحسين إعدادك. وكدليل تقريبي، لا كوعد، يكسب خادم منزلي واحد يشغّل من 10 إلى 15 خدمة نحو $30 إلى $100 شهريًا، وقد يكسب أقل من ذلك، حتى الصفر. وتضيف خوادم أكثر، أو حوسبة GPU، إلى ذلك.

**هل يمكنني التشغيل على VPS أو خادم سحابي؟**

تتطلب بعض الخدمات عنوان IP منزليًا ولن تدفع (أو ستحظر) عناوين IP الخاصة بـ VPS ومراكز البيانات. يُدرج الكتالوج "residential IP" (عنوان IP منزلي) ضمن ما تحتاج إليه. والخدمات التي تعمل على VPS طريقة جيدة للتوسع دون أجهزة منزلية إضافية.

**كيف تُخزَّن بيانات الاعتماد؟**

كل بيانات اعتماد الخدمات مشفّرة في حالة السكون في قاعدة بيانات SQLite باستخدام مفتاح Fernet مخزّن في `/data/.fernet_key`، يُولَّد تلقائيًا عند التشغيل الأول. ويوجد ملف قاعدة البيانات في وحدة تخزين Docker المركّبة (`cashpilot_data:/data`). ولا تُرسل بيانات الاعتماد أبدًا إلى أي مكان سوى حاويات الخدمات نفسها.

لاحظ أن هذا مفتاح مختلف عن `CASHPILOT_SECRET_KEY`، الذي لا يوقّع إلا جلسات تسجيل الدخول.

### النسخ الاحتياطي لمفتاح التشفير { #backing-up-the-encryption-key }

لا يمكن استعادة بيانات اعتمادك إلا بقدر ما يمكن استعادة `/data/.fernet_key`. إذا فقدت ذلك الملف فسيتعيّن عليك إعادة إدخال كل بيانات الاعتماد، لأنه لا توجد طريقة لفك تشفير القيم المخزّنة بدونه.

```bash
# Back it up
docker exec cashpilot-ui cat /data/.fernet_key

# Restore onto a fresh volume: pass the saved value when starting CashPilot.
# It must reach the container, so put it on the same command line (or export it,
# or set it in your .env) - a bare shell assignment on its own line does nothing.
CASHPILOT_ENCRYPTION_KEY=<the value you saved> docker compose up -d
```

للملف الأولوية دائمًا على متغير البيئة، لذلك فإن ضبط `CASHPILOT_ENCRYPTION_KEY` على نسخة لديها مفتاح بالفعل لا يغيّر شيئًا وهو آمن. ولا يُعتمد المتغير إلا عندما لا يوجد ملف مفتاح، وهذه بالضبط حالة الاستعادة.

إذا لم يستطع CashPilot كتابة المفتاح على القرص إطلاقًا، لأن `/data` غير قابل للكتابة أو غير مركّب، فإنه يرفض البدء بدلًا من تشفير بيانات اعتمادك بمفتاح يختفي عند إعادة التشغيل التالية. اضبط `CASHPILOT_ALLOW_EPHEMERAL_KEY=true` إذا كان هذا ما تريده فعلًا.

### نسيت كلمة المرور أو اسم المستخدم { #forgot-password-or-username }

لا يوفّر CashPilot إعادة تعيين عبر البريد الإلكتروني. فمن يشغّل الخادم يعيد تعيين كلمة المرور من وحدة التحكم (console) الخاصة بحاوية واجهة CashPilot. ولا تتأثر خدماتك وأرباحك وبيانات اعتمادك المحفوظة: فهي مشفّرة بالملف `/data/.fernet_key`، وليس بكلمة مرورك.

يحتاج الأمر `python -m app.users` إلى CashPilot 2.3 أو أحدث. وعلى الإصدار 2.2 أو ما قبله يفشل برسالة `No module named app.users`. حدّث أولًا: مع Docker Compose، غيّر وسمَي `drumsergio/cashpilot` و`drumsergio/cashpilot-worker` إلى `2.3` أو أحدث (فالتثبيت على وسم مثل `2.2` أو `2.2.9` يبقى على ذلك الإصدار)، ثم شغّل `docker compose up -d` ([تحديث CashPilot](getting-started.md#updating-cashpilot)). وعلى Unraid، حدّث الحاوية.

1. اسرد الحسابات. يعرض هذا أيضًا اسم المستخدم الذي نسيته. أسماء المستخدمين حساسة لحالة الأحرف.

    ```bash
    docker exec -it cashpilot-ui python -m app.users list
    ```

2. اضبط كلمة مرور عشوائية جديدة للحساب. استبدل `alice` باسم المستخدم من الخطوة 1.

    ```bash
    docker exec -it cashpilot-ui python -m app.users reset-password alice
    ```

    إذا كان هناك مالك واحد بالضبط يمكنك حذف اسم المستخدم، فيعيد الأمر تعيين كلمة مرور ذلك المالك. وإذا بدأ اسم المستخدم بـ `-`، فضع `--` قبله: `reset-password -- -alice`.

    يطبع الأمر كلمة المرور الجديدة مرة واحدة.

3. إذا كان من المحتمل أن شخصًا آخر وصل إلى الحساب، فأعد تشغيل حاوية الواجهة الآن (`docker restart cashpilot-ui`). فالمتصفحات التي كانت لا تزال مسجّلة الدخول بذلك المستخدم لا تُسجَّل خروجها إلا بعد إعادة التشغيل. وإذا كنت قد نسيت كلمة المرور فقط، فإعادة التشغيل اختيارية.
4. سجّل الدخول بكلمة المرور الجديدة، ثم غيّرها من قائمة الصورة الرمزية (أعلى اليمين)، **Change password** (تغيير كلمة المرور).

يعتمد اسم الحاوية على طريقة تثبيتك لـ CashPilot:

| التثبيت | حاوية الواجهة |
|---|---|
| `docker-compose.yml`، CasaOS | `cashpilot-ui` |
| Unraid | `cashpilot` (`docker exec -it cashpilot python -m app.users list`) |
| Runtipi | اسم مُولَّد؛ يعرضه `docker ps` |

ولدى Portainer وUnraid وCasaOS أيضًا زر وحدة تحكم للحاوية. لا يحتاج الأمر إلى إدخال من الطرفية، لذلك يعمل هناك أيضًا.

لتغيير اسم مستخدم:

```bash
docker exec -it cashpilot-ui python -m app.users rename OLD NEW
```

يتبع الاسم الجديد قاعدة التسجيل: من 3 إلى 32 حرفًا أو رقمًا أو `_` أو `-`. سجّل الخروج ثم الدخول مجددًا لتراه.

**بعد اختراق مشتبه به**، مثل فقدان نسخة احتياطية تحتوي على `/data/.secret_key`، لا تكفي إعادة تعيين كلمة المرور وحدها. فمن يملك ذلك المفتاح يستطيع توقيع ملف تعريف ارتباط صالح لتسجيل الدخول، وإعادة التعيين لا توقفه. استبدل المفتاح، ثم أعد تشغيل حاوية الواجهة. لا يعيد `&&` تشغيلها إلا عندما يكون المفتاح الجديد في مكانه؛ وإذا طبع الأمر خطأً، فأصلحه أولًا:

```bash
docker exec cashpilot-ui python -m app.users rotate-session-key && docker restart cashpilot-ui
```

بعد إعادة التشغيل يُسجَّل خروج كل متصفح، ويسجّل الجميع الدخول مجددًا بكلمات مرورهم. ولا تتأثر بيانات الاعتماد المحفوظة. وإذا كنت قد ضبطت `CASHPILOT_SECRET_KEY` بنفسك، فإن الأمر يرفض التنفيذ: ضع قيمة عشوائية جديدة في ذلك المتغير وأعد إنشاء الحاوية بدلًا من ذلك. أما `docker run` من صورة الحاوية فلا يرى ذلك المتغير ولا يستطيع الرفض، لذلك استخدم `docker exec` على حاوية الواجهة.

ينهي المفتاح الجديد ملفات تعريف الارتباط المزوّرة، لكنه لا يلغي ما فعله المهاجم أثناء وجوده. خطوتان إضافيتان:

1. شغّل `docker exec cashpilot-ui python -m app.users list`. واحذف من لوحة التحكم أي حساب لا تعرفه.
2. إذا كانت النسخة المفقودة تحتوي على `/data` بالكامل، فغيّر كلمات مرور حساباتك لدى المزوّدين. فالملفان `.fernet_key` و`cashpilot.db` معًا يفكّان تشفير كل بيانات الاعتماد المحفوظة.

إذا استعدت لاحقًا نسخة احتياطية أُخذت قبل تدوير المفتاح، فاستبعد منها `.secret_key` ([النسخ الاحتياطي والاستعادة](backup-restore.md#restore))، أو دوّر المفتاح وأعد التشغيل مرة أخرى. وإلا فسيعود المفتاح القديم. كما تعيد قاعدة البيانات المستعادة الحسابات وكلمات المرور التي كانت تحتويها، لذلك كرّر فحص الحسابات وأي إعادة تعيين لكلمات المرور.

**إذا لم تبدأ حاوية الواجهة**، فشغّل الأمر من صورة الحاوية نفسها على البيانات نفسها. أولًا ابحث عن مجلد المضيف الذي يحتوي على `/data` الخاص بالواجهة. يعمل هذا مع حاوية متوقفة، ومع وحدة تخزين مسمّاة وكذلك مع الربط المباشر (bind mount) (Unraid، CasaOS، Runtipi):

```bash
docker inspect -f '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}' cashpilot-ui
```

ثم ركّب ذلك المجلد واستخدم وسم صورة الحاوية الذي تشغّله:

```bash
docker run --rm -v "<folder>:/data" --entrypoint python drumsergio/cashpilot:<same tag> -m app.users list
```

تحقّق من أن القائمة تعرض حساباتك، ثم شغّل السطر نفسه مع `reset-password alice` بدلًا من `list`.

المسار الذي لا قاعدة بيانات فيه يعطي الخطأ "no database"، ولا ينشئ الأمر ولا يغيّر أي شيء هناك. وقد يترك Docker مع ذلك مجلدًا فارغًا أو وحدة تخزين فارغة بذلك الاسم؛ فاحذفها.

**لا** تحذف وحدة تخزين البيانات: فهذا يمحو `/data/.fernet_key` ومعه كل بيانات الاعتماد المحفوظة. و**لا** تحذف أيضًا صفوفًا من الجدول `users`.

**كيف أزيل CashPilot بالكامل؟**

لا يزيل `docker compose down -v` إلا حاويات CashPilot نفسه. فالخدمات التي نشرها تستمر في العمل، وتبقى بياناتها، والشبكة المحاطة بالحاجز، وجدول جدار الحماية. تشرح صفحة [إزالة CashPilot بالكامل](uninstall.md) كيفية إزالة كل ذلك، وما الذي يضيع نهائيًا، وكيف تتحقق من أنه لم يبقَ شيء.

**ماذا عن الأمان؟**

كل خدمة ينشرها CashPilot تعمل في حاويتها الخاصة مع إسقاط كل صلاحيات Linux (capabilities) (تعيد بعض الخدمات فقط الصلاحيات التي تعلنها) ومع ضبط `--security-opt no-new-privileges`، لذلك لا تستطيع أي عملية في الداخل اكتساب صلاحيات. ولا تستطيع الحاويات رؤية نظام ملفات المضيف خارج وحدات التخزين التي تعلنها الخدمة. وفي التثبيت الجديد يعزلها العامل أيضًا بحاجز عن شبكتك المحلية (LAN)، والمضيف، وشبكة tailnet الخاصة بك، والبيانات الوصفية السحابية، لذلك تصل إلى الإنترنت ولا شيء محلي ([عزل الشبكة](isolation.md)). وعلى Podman لا يتوفر الحاجز: تعمل تطبيقات الربح على شبكة Podman الافتراضية، التي تستطيع الوصول إلى شبكتك المحلية، وتذكر صفحة **Fleet** (الأسطول) ذلك (تسرد صفحة [عزل الشبكة](isolation.md) الخيارات). والتثبيت الذي رُقّي من إصدار سابق للإصدار 1.70 يُبقي تطبيقات الربح على الجسر الافتراضي لـ Docker، الذي يستطيع الوصول إلى شبكتك المحلية، إلى أن تنقر **Turn on isolation** (تشغيل العزل) في صفحة **Fleet** (الأسطول). ومنذ الإصدار 2.0.7 يعمل Mysterium خلف الحاجز أيضًا؛ أما العقدة المنشورة حتى الإصدار 2.0.6 فتبقى على شبكة المضيف إلى أن تعيد نشرها ([نقل عقدة Mysterium خلف الحاجز](mysterium-fence.md)). وتشرح صفحة [حماية شبكتك المنزلية](home-network-security.md) بديلًا هو وضع جدار حماية على الجسر الخاص بك. تُشفَّر بيانات اعتماد الخدمات في حالة السكون باستخدام تشفير Fernet المتماثل. ولا تصل الواجهة إلى Docker. ومع ملفات compose المرفقة لا يُعطى العامل أبدًا مقبس Docker الخام: بل يصل إلى Docker عبر `cashpilot-socket-proxy`، الذي يرفض الحاويات ذات الامتيازات وربط `/` أو المقبس (إلا إذا وضعت أحدهما، أو مجلدًا فوق المقبس، في `CASHPILOT_PROXY_BIND_MOUNTS` أو `CASHPILOT_COMPOSE_DIR`: فالوكيل يقبلها كما هي)، ويقصر العامل على الحاويات ووحدات التخزين والشبكات التي تحمل تسمية المالك الخاصة به ([الإعدادات الأمنية الافتراضية](security-defaults.md)). أما قوالب Unraid وتطبيق TrueNAS فلا تزال تركّب المقبس الخام في العامل، وهذا يعني صلاحيات root على المضيف ([متاجر التطبيقات](app-stores.md)).

ومع ذلك، لا يوجد إعداد منيع تمامًا. فأنت لا تزال تشغّل برامج من جهات خارجية توجّه حركة مرور خارجية عبر شبكتك. يقلّل عزل Docker سطح الهجوم كثيرًا مقارنةً بتشغيل هذه الخدمات مباشرةً على مضيفك، لكنه لا يزيل كل المخاطر. نوصي بتشغيل CashPilot على جهاز مخصّص أو VLAN، وإبقاء Docker ونظام تشغيل المضيف محدّثين، ومراجعة الكود مفتوح المصدر لأي خدمة قبل نشرها.

**ماذا يحدث إذا تعطّلت حاوية خدمة؟**

يراقب CashPilot سلامة الحاويات باستمرار. إذا خرجت حاوية خدمة بشكل غير متوقع، فإنها تُعاد تشغيلها تلقائيًا. وتعرض لوحة التحكم مدة التشغيل وحالة السلامة لكل خدمة قيد التشغيل.

**لا تبدأ عقدة Mysterium الخاصة بي بعد إعادة النشر. لماذا؟**

السبب الأكثر شيوعًا منفذ في نطاق UDP الخاص بها يحتجزه بالفعل برنامج آخر على المضيف. يجب على Docker حجز كل منفذ في النطاق، لذلك يكفي منفذ واحد مشغول لمنع البدء. تشرح صفحة [اختيار نطاق منافذ UDP](mysterium-fence.md#choosing-the-udp-port-range) كيف تختار نطاقًا يبقى حرًّا.

**نسختي عبر بروكسي تعمل لكنها لا تكسب شيئًا. لماذا؟**

قد يرفض البروكسي الاتصال بخوادم تطبيق الربح ذاك، أو لا يسمح إلا بالمنفذين 80 و443. ولا يتحقق **Test** (اختبار) في CashPilot إلا من أن البروكسي يصل إلى الإنترنت. تشرح صفحة [افحص خوادم تطبيق الربح عبر البروكسي](proxies.md#probe-an-earners-servers-through-the-proxy) كيف تتحقق من المضيف والمنفذ الخاصين بتطبيق الربح نفسه.

**ما الخدمات الثقيلة، وأين يجب أن تعمل؟**

عُقد التخزين، والمرحّلات (relays) ومخارج VPN، وأعمال GPU هي الأكثر استهلاكًا. تسرد صفحة [ميزانية جهاز صغير](fleet.md#budgeting-a-small-box) هذه الخدمات وتشرح كيف تقيس كل حاوية قبل أن تقرر.

<a id="worker-lost-docker"></a>

### فقد العامل الاتصال بـ Docker بعد تحديث Docker { #the-worker-lost-docker-after-a-docker-update }

**ما تراه.** يبقى العامل متصلًا في صفحة **Fleet** (الأسطول)، لكن CashPilot لا يستطيع تشغيل حاوياته أو إيقافها أو تحديثها. تعرض صفحة **Fleet** (الأسطول) العبارة **Docker unreachable** (تعذّر الوصول إلى Docker) بجانب العامل. وبعد 10 دقائق يفشل فحص السلامة (healthcheck) الخاص بالعامل (يعرض `docker ps` العامل بالحالة `unhealthy`). وبعد 30 دقيقة يقول الجرس وإشعاراتك إن العامل لا يستطيع الوصول إلى Docker. ويعرض `docker logs cashpilot-socket-proxy` الرسالة `upstream Docker socket unreachable`، ومع ملف compose حالي يعرض `docker ps` الوكيل بالحالة `unhealthy` في غضون 3 دقائق تقريبًا. وتستمر تطبيقات الربح لديك في العمل.

**السبب.** تربط ملفات compose المرفقة ملف المقبس `/var/run/docker.sock` داخل `cashpilot-socket-proxy`. وربط ملف يحتجز ذلك الملف بعينه. يعيد تحديث Docker (مثل تثبيت `unattended-upgrades` لإصدار جديد من `docker-ce`) تشغيل Docker، فينشئ Docker ملف مقبس جديدًا في المسار نفسه. ومع تفعيل live-restore في Docker، يستمر الوكيل في العمل خلال إعادة التشغيل تلك ويحتفظ بالملف القديم. ولا شيء يجيب على الملف القديم.

**إصلاح سريع.** على ذلك الجهاز، أعد تشغيل الوكيل:

```bash
docker restart cashpilot-socket-proxy
```

تربط إعادة التشغيل المقبس الجديد، ويجد العامل Docker مجددًا عند نبضة الاتصال التالية. لا تحتاج إلى إعادة تشغيل العامل. على Unraid وTrueNAS يحتجز العامل المقبس بنفسه، لذلك أعد تشغيل العامل.

**إصلاح دائم.** اربط مجلد المقبس، لا ملف المقبس. فربط المجلد يُظهر المقبس المستبدَل فورًا. في الخدمة `cashpilot-socket-proxy` في ملف compose الخاص بك، استبدل السطر `- /var/run/docker.sock:/var/run/docker.sock:ro` بالربط أدناه، وأضف السطر `SOCKGUARD_UPSTREAM_SOCKET` إلى `environment` الخاص بها:

```yaml
    volumes:
      - type: bind
        source: /var/run
        target: /host-run
        read_only: true
        bind:
          recursive: disabled
      - cashpilot_docker_api:/run/cashpilot-docker
    environment:
      # Keep the lines that are already there, and add this one:
      - SOCKGUARD_UPSTREAM_SOCKET=/host-run/docker.sock
```

ثم شغّل `docker compose up -d`. ويعمل التغيير نفسه في `docker-compose.worker.yml` و`docker-compose.fleet.yml`. لا يقرأ Compose هذين الملفين إلا عندما تسمّيهما، لذلك شغّل `docker compose -f docker-compose.worker.yml up -d` أو `docker compose -f docker-compose.fleet.yml up -d`، إلا إذا كان `COMPOSE_FILE` يسمّي الملف بالفعل.

- `recursive: disabled` ضروري. يحتوي `/var/run` على نقاط تركيب أخرى، مثل نطاقات أسماء الشبكة (network namespaces) الخاصة بـ Docker تحت `/run/docker/netns` و`/run/user/...`. والربط التكراري يُدخلها كلها إلى الوكيل. أما الربط غير التكراري فلا يُظهر إلا المجلد نفسه.
- يوجّه `SOCKGUARD_UPSTREAM_SOCKET` الوكيل إلى المسار الجديد. وتبقى كتلة السياسة وبصمتها كما هي، لأن متغير البيئة يتجاوز `upstream.socket` في السياسة. وبدون المتغير لا يبدأ الوكيل (`upstream socket not found (/var/run/docker.sock)`).
- يمكن أن يحتفظ `cashpilot-migrate` بربط الملف. فهو يبدأ من جديد عند كل `docker compose up`، لذلك يحصل دائمًا على المقبس الحالي. وإذا أعطيته ربط المجلد نفسه، فأضف `DOCKER_HOST=unix:///host-run/docker.sock` إلى `environment` الخاص به. يقرأ العامل 2.8.4 وما بعده هذا المتغير. ولا توجّهه أبدًا إلى مقبس الوكيل: فأداة الترحيل تحتاج إلى مقبس المضيف نفسه.
- يعطي ربط المجلد الوكيل كل مقبس في `/var/run`، لا مقبس Docker وحده. وعلى خادم نموذجي يشمل ذلك مقبس systemd نفسه، وD-Bus، ومقابس أدوات مثل Tailscale أو snapd. ولا يمنع `read_only` برنامجًا من الاتصال بمقبس، والوكيل يعمل بصلاحيات root. والوصول إلى مقبس Docker يعطي بالفعل صلاحيات root على المضيف، لذلك لا يكسب الوكيل المخترَق إلا القليل مما لم يكن لديه. إذا أردت ألا يحتجز الوكيل إلا مقبس Docker، فاحتفظ بربط الملف وأعد تشغيل الوكيل بعد كل تحديث لـ Docker: فالتنبيه أعلاه يخبرك بالموعد.
- يحتاج إلى Docker Compose 2.30.0 أو أحدث. فالإصدارات الأقدم ترفض الملف كله برسالة `Additional property recursive is not allowed`. شغّل `docker compose version` للتحقق. يحزم Debian 13 الإصدار Compose 2.26.1، لذلك ثبّت Compose على Debian من مستودع Docker نفسه. ويستخدم التحديث من داخل التطبيق إصداره الخاص Compose 2.33، لذلك يقرأ الملف المعدَّل.
- لا يعمل إلا على Linux. فـ Docker Desktop على macOS وWindows لا يربط إلا `/var/run/docker.sock` داخل آلته الافتراضية. وهناك يكون `/var/run` مجلدًا على جهاز Mac أو PC الخاص بك، بلا مقبس Docker فيه.
- مع Docker بلا صلاحيات root (rootless) يوجد المقبس في `/run/user/<your uid>`، وهو نقطة تركيب منفصلة. استخدم ذلك المجلد قيمةً لـ `source`.
- على Podman، احتفظ بربط الملف. لم نختبر ربط المجلد هناك.

تحتفظ الملفات المرفقة بربط الملف، لأن ربط المجلد يحتاج إلى Compose 2.30 وLinux، بينما يدعم CashPilot أيضًا إصدارات Compose الأقدم وDocker Desktop. وملف compose الأحدث الذي تنزّله لا يحتوي على تغييرك، لذلك أعد إجراءه بعد أن تستبدل الملف.

# คำถามที่พบบ่อย { #faq }

**การแบ่งปันแบนด์วิดท์ปลอดภัยไหม**

โดยทั่วไป บริการแบ่งปันแบนด์วิดท์จะส่งทราฟฟิกที่ชอบด้วยกฎหมาย (การวิจัยตลาด การตรวจสอบโฆษณา การเปรียบเทียบราคา การส่งเนื้อหา) ผ่านการเชื่อมต่อของคุณ อย่างไรก็ตาม คุณกำลังแบ่งปันที่อยู่ IP ของตัวเอง จึงควรอ่านข้อกำหนดการให้บริการและนโยบายความเป็นส่วนตัวของแต่ละบริการอย่างละเอียดก่อนสมัคร สำหรับบางบริการ การรันบน VPS แทน IP ที่อยู่อาศัยก็เป็นทางเลือกหนึ่ง **นี่ไม่ใช่คำแนะนำทางกฎหมาย -- ให้สอบถามบริการที่ตั้งใจจะใช้ และหากจำเป็น ให้ขอคำปรึกษาทางกฎหมายที่เป็นอิสระเกี่ยวกับเขตอำนาจศาลของคุณ**

**หารายได้ได้เท่าไร**

รายได้แตกต่างกันมากตามสถานที่ ผู้ให้บริการอินเทอร์เน็ต จำนวนอุปกรณ์ และบริการที่รัน แดชบอร์ดติดตามรายได้จริงตามเวลา เพื่อให้ปรับการตั้งค่าให้ดีที่สุดได้ เป็นแนวทางคร่าว ๆ ไม่ใช่คำสัญญา: โฮมเซิร์ฟเวอร์หนึ่งเครื่องที่รัน 10 ถึง 15 บริการทำรายได้ประมาณ $30 ถึง $100 ต่อเดือน และอาจได้น้อยกว่านั้นจนถึงศูนย์ เซิร์ฟเวอร์ที่มากขึ้น หรือการประมวลผลด้วย GPU จะเพิ่มรายได้จากตรงนั้น

**รันบน VPS หรือคลาวด์เซิร์ฟเวอร์ได้ไหม**

บางบริการต้องใช้ IP ที่อยู่อาศัย และจะไม่จ่ายเงิน (หรือจะแบน) IP ของ VPS/ดาต้าเซ็นเตอร์ แคตตาล็อกระบุ "residential IP" ไว้ในสิ่งที่บริการต้องการ บริการที่ทำงานบน VPS ได้เป็นวิธีที่ดีในการขยายขนาดโดยไม่ต้องเพิ่มฮาร์ดแวร์ในบ้าน

**ข้อมูลรับรองถูกจัดเก็บอย่างไร**

ข้อมูลรับรองของบริการทั้งหมดถูกเข้ารหัสขณะจัดเก็บในฐานข้อมูล SQLite ด้วยคีย์ Fernet ที่เก็บไว้ที่ `/data/.fernet_key` ซึ่งสร้างขึ้นอัตโนมัติในการรันครั้งแรก ไฟล์ฐานข้อมูลอยู่ใน Docker volume ที่ mount ไว้ (`cashpilot_data:/data`) ข้อมูลรับรองไม่เคยถูกส่งไปที่ใด ยกเว้นคอนเทนเนอร์ของบริการเอง

โปรดทราบว่าคีย์นี้เป็นคนละคีย์กับ `CASHPILOT_SECRET_KEY` ซึ่งใช้ลงนามเซสชันการเข้าสู่ระบบเท่านั้น

### การสำรองคีย์เข้ารหัส { #backing-up-the-encryption-key }

ข้อมูลรับรองกู้คืนได้ก็ต่อเมื่อยังมี `/data/.fernet_key` หากไฟล์นั้นหายไป จะต้องป้อนข้อมูลรับรองทุกรายการใหม่ เพราะไม่มีทางถอดรหัสค่าที่จัดเก็บไว้ได้หากไม่มีไฟล์นี้

```bash
# Back it up
docker exec cashpilot-ui cat /data/.fernet_key

# Restore onto a fresh volume: pass the saved value when starting CashPilot.
# It must reach the container, so put it on the same command line (or export it,
# or set it in your .env) - a bare shell assignment on its own line does nothing.
CASHPILOT_ENCRYPTION_KEY=<the value you saved> docker compose up -d
```

ไฟล์มีลำดับความสำคัญเหนือตัวแปรสภาพแวดล้อมเสมอ การตั้งค่า `CASHPILOT_ENCRYPTION_KEY` บนระบบที่มีคีย์อยู่แล้วจึงไม่เปลี่ยนอะไรและปลอดภัย ค่านี้ถูกใช้เฉพาะเมื่อไม่มีไฟล์คีย์ ซึ่งก็คือกรณีกู้คืนพอดี

หาก CashPilot เขียนคีย์ลงดิสก์ไม่ได้เลย เพราะ `/data` เขียนไม่ได้หรือไม่ได้ mount ไว้ ระบบจะปฏิเสธการเริ่มทำงาน แทนที่จะเข้ารหัสข้อมูลรับรองด้วยคีย์ที่หายไปในการรีสตาร์ตครั้งถัดไป ตั้งค่า `CASHPILOT_ALLOW_EPHEMERAL_KEY=true` หากต้องการแบบนั้นจริง ๆ

### ลืมรหัสผ่านหรือชื่อผู้ใช้ { #forgot-password-or-username }

CashPilot ไม่มีการรีเซ็ตผ่านอีเมล ผู้ที่ดูแลเซิร์ฟเวอร์จะรีเซ็ตรหัสผ่านจากคอนโซลของคอนเทนเนอร์ CashPilot UI บริการ รายได้ และข้อมูลรับรองที่บันทึกไว้จะไม่ได้รับผลกระทบ เพราะเข้ารหัสด้วย `/data/.fernet_key` ไม่ใช่ด้วยรหัสผ่าน

คำสั่ง `python -m app.users` ต้องใช้ CashPilot 2.3 ขึ้นไป บน 2.2 หรือเก่ากว่าจะล้มเหลวด้วย `No module named app.users` ให้อัปเดตก่อน: สำหรับ Docker Compose ให้เปลี่ยนแท็ก `drumsergio/cashpilot` และ `drumsergio/cashpilot-worker` เป็น `2.3` หรือใหม่กว่า (การปักหมุดอย่าง `2.2` หรือ `2.2.9` จะอยู่กับรุ่นนั้น) แล้วรัน `docker compose up -d` ([การอัปเดต CashPilot](getting-started.md#updating-cashpilot)) บน Unraid ให้อัปเดตคอนเทนเนอร์

1. แสดงรายการบัญชี ซึ่งจะแสดงชื่อผู้ใช้ที่ลืมไปด้วย ชื่อผู้ใช้แยกตัวพิมพ์เล็กและใหญ่

    ```bash
    docker exec -it cashpilot-ui python -m app.users list
    ```

2. ตั้งรหัสผ่านสุ่มใหม่ให้บัญชีนั้น แทน `alice` ด้วยชื่อผู้ใช้จากขั้นที่ 1

    ```bash
    docker exec -it cashpilot-ui python -m app.users reset-password alice
    ```

    หากมีเจ้าของเพียงคนเดียว ไม่ต้องระบุชื่อผู้ใช้ก็ได้ แล้วคำสั่งจะรีเซ็ตเจ้าของคนนั้น หากชื่อผู้ใช้ขึ้นต้นด้วย `-` ให้ใส่ `--` ไว้ข้างหน้า: `reset-password -- -alice`

    คำสั่งจะพิมพ์รหัสผ่านใหม่ออกมาครั้งเดียว

3. หากอาจมีคนอื่นเคยเข้าถึงบัญชีนั้น ให้รีสตาร์ตคอนเทนเนอร์ UI ทันที (`docker restart cashpilot-ui`) เบราว์เซอร์ที่ยังเข้าสู่ระบบเป็นผู้ใช้นั้นอยู่จะออกจากระบบหลังการรีสตาร์ตเท่านั้น หากแค่ลืมรหัสผ่าน การรีสตาร์ตก็ไม่จำเป็น
4. เข้าสู่ระบบด้วยรหัสผ่านใหม่ แล้วเปลี่ยนรหัสผ่านจากเมนูรูปโปรไฟล์ (มุมขวาบน) **Change password** (เปลี่ยนรหัสผ่าน)

ชื่อคอนเทนเนอร์ขึ้นอยู่กับวิธีที่ติดตั้ง CashPilot:

| การติดตั้ง | คอนเทนเนอร์ UI |
|---|---|
| `docker-compose.yml`, CasaOS | `cashpilot-ui` |
| Unraid | `cashpilot` (`docker exec -it cashpilot python -m app.users list`) |
| Runtipi | ชื่อที่สร้างขึ้นเอง `docker ps` แสดงชื่อนั้น |

Portainer, Unraid และ CasaOS มีปุ่มคอนโซลสำหรับคอนเทนเนอร์ด้วย คำสั่งนี้ไม่ต้องรับข้อมูลจากเทอร์มินัล จึงใช้ที่นั่นได้เช่นกัน

หากต้องการเปลี่ยนชื่อผู้ใช้:

```bash
docker exec -it cashpilot-ui python -m app.users rename OLD NEW
```

ชื่อใหม่ต้องเป็นไปตามกฎการลงทะเบียน: ตัวอักษร ตัวเลข `_` หรือ `-` ยาว 3 ถึง 32 ตัว ออกจากระบบแล้วเข้าสู่ระบบใหม่เพื่อดูชื่อนั้น

**หลังจากสงสัยว่าถูกเจาะระบบ** เช่น ข้อมูลสำรองที่มี `/data/.secret_key` หายไป การรีเซ็ตรหัสผ่านอย่างเดียวไม่พอ ผู้ที่มีคีย์นั้นสามารถลงนามคุกกี้การเข้าสู่ระบบที่ถูกต้องได้ และการรีเซ็ตไม่ได้หยุดสิ่งนั้น ให้เปลี่ยนคีย์ แล้วรีสตาร์ตคอนเทนเนอร์ UI `&&` จะรีสตาร์ตเฉพาะเมื่อคีย์ใหม่พร้อมแล้ว หากคำสั่งพิมพ์ข้อผิดพลาด ให้แก้ไขก่อน:

```bash
docker exec cashpilot-ui python -m app.users rotate-session-key && docker restart cashpilot-ui
```

หลังการรีสตาร์ต ทุกเบราว์เซอร์จะออกจากระบบ และทุกคนต้องเข้าสู่ระบบใหม่ด้วยรหัสผ่านของตัวเอง ข้อมูลรับรองที่บันทึกไว้ไม่ได้รับผลกระทบ หากตั้ง `CASHPILOT_SECRET_KEY` เอง คำสั่งจะปฏิเสธ: ให้ใส่ค่าสุ่มใหม่ในตัวแปรนั้นแล้วสร้างคอนเทนเนอร์ใหม่แทน `docker run` จากอิมเมจไม่เห็นตัวแปรนั้นและปฏิเสธไม่ได้ จึงต้องใช้ `docker exec` กับคอนเทนเนอร์ UI

คีย์ใหม่หยุดคุกกี้ปลอมได้ แต่ไม่ได้ย้อนสิ่งที่ผู้โจมตีทำไปแล้วระหว่างที่อยู่ในระบบ มีอีกสองขั้นตอน:

1. รัน `docker exec cashpilot-ui python -m app.users list` ลบบัญชีที่ไม่รู้จักจากแดชบอร์ด
2. หากสำเนาที่หายไปมี `/data` ทั้งหมด ให้เปลี่ยนรหัสผ่านของบัญชีผู้ให้บริการ เพราะ `.fernet_key` และ `cashpilot.db` รวมกันถอดรหัสข้อมูลรับรองที่บันทึกไว้ได้ทุกรายการ

หากภายหลังกู้คืนข้อมูลสำรองที่ทำไว้ก่อนการเปลี่ยนคีย์ ให้เว้น `.secret_key` ของข้อมูลสำรองนั้นไว้ ([การสำรองและกู้คืนข้อมูล](backup-restore.md#restore)) หรือเปลี่ยนคีย์และรีสตาร์ตอีกครั้ง มิฉะนั้นคีย์เก่าจะกลับมา ฐานข้อมูลที่กู้คืนยังนำบัญชีและรหัสผ่านที่เคยมีกลับมาด้วย จึงต้องตรวจสอบบัญชีและรีเซ็ตรหัสผ่านซ้ำ

**หากคอนเทนเนอร์ UI ไม่เริ่มทำงาน** ให้รันคำสั่งจากอิมเมจเดียวกันกับข้อมูลชุดเดียวกัน ก่อนอื่นให้หาโฟลเดอร์บนโฮสต์ที่เก็บ `/data` ของ UI วิธีนี้ใช้ได้กับคอนเทนเนอร์ที่หยุดอยู่ และใช้ได้ทั้งกับ named volume และ bind mount (Unraid, CasaOS, Runtipi):

```bash
docker inspect -f '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}' cashpilot-ui
```

จากนั้น mount โฟลเดอร์นั้นและใช้แท็กอิมเมจที่รันอยู่:

```bash
docker run --rm -v "<folder>:/data" --entrypoint python drumsergio/cashpilot:<same tag> -m app.users list
```

ตรวจสอบว่ารายการแสดงบัญชีของคุณ แล้วรันบรรทัดเดียวกันโดยใช้ `reset-password alice` แทน `list`

พาธที่ไม่มีฐานข้อมูลจะให้ข้อผิดพลาด "no database" และคำสั่งจะไม่สร้างหรือเปลี่ยนอะไรที่นั่น แต่ Docker อาจยังทิ้งโฟลเดอร์หรือ volume ว่างที่มีชื่อนั้นไว้ ให้ลบทิ้ง

**อย่า** ลบ data volume เพราะจะลบ `/data/.fernet_key` และข้อมูลรับรองที่บันทึกไว้ทุกรายการไปด้วย และ **อย่า** ลบแถวจากตาราง `users` เช่นกัน

**จะลบ CashPilot ออกทั้งหมดได้อย่างไร**

`docker compose down -v` ลบเฉพาะคอนเทนเนอร์ของ CashPilot เอง บริการที่ CashPilot ติดตั้งใช้งานไว้ยังทำงานต่อ และข้อมูลของบริการเหล่านั้น เครือข่ายที่มีรั้วกั้น และตารางไฟร์วอลล์ยังอยู่ [การลบ CashPilot ออกทั้งหมด](uninstall.md) ลบทุกอย่าง บอกว่าอะไรจะหายไปถาวร และแสดงวิธีตรวจสอบว่าไม่มีอะไรเหลืออยู่

**แล้วเรื่องความปลอดภัยล่ะ**

ทุกบริการที่ CashPilot ติดตั้งใช้งานจะรันในคอนเทนเนอร์ของตัวเองโดยตัด Linux capability ทั้งหมดออก (มีบางบริการที่เพิ่มกลับเฉพาะ capability ที่ประกาศไว้) และตั้ง `--security-opt no-new-privileges` ไว้ โปรเซสข้างในจึงยกระดับสิทธิ์ไม่ได้ คอนเทนเนอร์มองไม่เห็นระบบไฟล์ของโฮสต์ นอกเหนือจาก volume ที่บริการประกาศไว้ ในการติดตั้งใหม่ เวิร์กเกอร์ยังกั้นคอนเทนเนอร์ออกจาก LAN โฮสต์ tailnet และ cloud metadata ด้วย คอนเทนเนอร์จึงเข้าถึงอินเทอร์เน็ตได้แต่เข้าถึงสิ่งใดในเครื่องไม่ได้ ([การแยกเครือข่าย](isolation.md)) บน Podman ไม่มีรั้วกั้นให้ใช้: แอปหารายได้รันบนเครือข่ายเริ่มต้นของ Podman ซึ่งเข้าถึง LAN ได้ และหน้า **Fleet** (กลุ่มเครื่อง) แจ้งเรื่องนี้ไว้ ([การแยกเครือข่าย](isolation.md) มีรายการทางเลือก) การติดตั้งที่อัปเกรดจากรุ่นก่อน 1.70 จะให้แอปหารายได้อยู่บน bridge เริ่มต้นของ Docker ซึ่งเข้าถึง LAN ได้ จนกว่าจะคลิก **Turn on isolation** (เปิดการแยก) ในหน้า **Fleet** (กลุ่มเครื่อง) ตั้งแต่ 2.0.7 Mysterium ก็รันหลังรั้วกั้นด้วย โหนดที่ติดตั้งใช้งานด้วย 2.0.6 หรือก่อนหน้าจะอยู่บนเครือข่ายของโฮสต์จนกว่าจะติดตั้งใช้งานใหม่ ([การย้ายโหนด Mysterium ไปอยู่หลังรั้วกั้น](mysterium-fence.md)) [การปกป้องเครือข่ายในบ้าน](home-network-security.md) อธิบายการตั้งไฟร์วอลล์ให้ bridge ของคุณเองแทน ข้อมูลรับรองของบริการเข้ารหัสขณะจัดเก็บด้วยการเข้ารหัสแบบสมมาตร Fernet UI ไม่มีสิทธิ์เข้าถึง Docker เมื่อใช้ไฟล์ compose ที่มาพร้อมกัน เวิร์กเกอร์จะไม่ได้ Docker socket ดิบเลย: เข้าถึง Docker ผ่าน `cashpilot-socket-proxy` ซึ่งปฏิเสธคอนเทนเนอร์แบบ privileged และการ bind `/` หรือ socket (เว้นแต่จะใส่อย่างใดอย่างหนึ่ง หรือโฟลเดอร์ที่อยู่เหนือ socket ไว้ใน `CASHPILOT_PROXY_BIND_MOUNTS` หรือ `CASHPILOT_COMPOSE_DIR` ซึ่ง proxy จะยอมรับตามที่ระบุ) และจำกัดเวิร์กเกอร์ไว้กับคอนเทนเนอร์ volume และเครือข่ายที่มีป้ายกำกับเจ้าของของเวิร์กเกอร์ ([ค่าเริ่มต้นด้านความปลอดภัย](security-defaults.md)) เทมเพลต Unraid และแอป TrueNAS ยังคง mount socket ดิบเข้าเวิร์กเกอร์ ซึ่งเท่ากับเป็น root บนโฮสต์ ([ร้านแอป](app-stores.md))

อย่างไรก็ตาม ไม่มีการตั้งค่าใดที่ปลอดภัยสมบูรณ์ คุณยังคงรันซอฟต์แวร์ของบุคคลที่สามที่ส่งทราฟฟิกภายนอกผ่านเครือข่ายของคุณ การแยกด้วย Docker ลดพื้นผิวการโจมตีได้มากเมื่อเทียบกับการรันบริการเหล่านี้บนโฮสต์โดยตรง แต่ไม่ได้ขจัดความเสี่ยงทั้งหมด เราแนะนำให้รัน CashPilot บนเครื่องหรือ VLAN เฉพาะ อัปเดต Docker และระบบปฏิบัติการของโฮสต์ให้ทันสมัยอยู่เสมอ และตรวจสอบโค้ดโอเพนซอร์สของบริการใดก็ตามก่อนติดตั้งใช้งาน

**จะเกิดอะไรขึ้นหากคอนเทนเนอร์ของบริการล่ม**

CashPilot เฝ้าดูสุขภาพของคอนเทนเนอร์อย่างต่อเนื่อง หากคอนเทนเนอร์ของบริการหยุดทำงานโดยไม่คาดคิด ระบบจะรีสตาร์ตให้อัตโนมัติ แดชบอร์ดแสดงเวลาทำงานและสถานะสุขภาพของทุกบริการที่กำลังรัน

**โหนด Mysterium ไม่เริ่มทำงานหลังติดตั้งใช้งานใหม่ เพราะอะไร**

สาเหตุที่พบบ่อยที่สุดคือมีพอร์ตในช่วง UDP ที่โปรแกรมอื่นบนโฮสต์ใช้อยู่แล้ว Docker ต้องจองทุกพอร์ตในช่วงนั้น พอร์ตที่ไม่ว่างเพียงพอร์ตเดียวจึงทำให้เริ่มทำงานไม่ได้ [การเลือกช่วงพอร์ต UDP](mysterium-fence.md#choosing-the-udp-port-range) อธิบายวิธีเลือกช่วงที่ยังว่างอยู่

**สำเนาผ่านพร็อกซีทำงานอยู่แต่ไม่มีรายได้ เพราะอะไร**

พร็อกซีอาจปฏิเสธการเชื่อมต่อไปยังเซิร์ฟเวอร์ของแอปหารายได้นั้น หรืออนุญาตเฉพาะพอร์ต 80 และ 443 ปุ่ม **Test** (ทดสอบ) ของ CashPilot ตรวจสอบเพียงว่าพร็อกซีเข้าถึงอินเทอร์เน็ตได้ [ตรวจสอบเซิร์ฟเวอร์ของแอปหารายได้ผ่านพร็อกซี](proxies.md#probe-an-earners-servers-through-the-proxy) แสดงวิธีตรวจสอบโฮสต์และพอร์ตของแอปหารายได้เอง

**บริการใดใช้ทรัพยากรมาก และควรรันที่ไหน**

โหนดพื้นที่จัดเก็บ รีเลย์และทางออก VPN และงาน GPU ใช้ทรัพยากรมากที่สุด [การจัดสรรทรัพยากรให้เครื่องขนาดเล็ก](fleet.md#budgeting-a-small-box) มีรายการบริการเหล่านี้ และแสดงวิธีวัดแต่ละคอนเทนเนอร์ก่อนตัดสินใจ

<a id="worker-lost-docker"></a>

### เวิร์กเกอร์เข้าถึง Docker ไม่ได้หลังอัปเดต Docker { #the-worker-lost-docker-after-a-docker-update }

**สิ่งที่เห็น** เวิร์กเกอร์ยังออนไลน์อยู่ในหน้า **Fleet** (กลุ่มเครื่อง) แต่ CashPilot เริ่ม หยุด หรืออัปเดตคอนเทนเนอร์ของเวิร์กเกอร์ไม่ได้ หน้า **Fleet** (กลุ่มเครื่อง) แสดง **Docker unreachable** (เข้าถึง Docker ไม่ได้) ข้างเวิร์กเกอร์ หลังจาก 10 นาที healthcheck ของเวิร์กเกอร์จะล้มเหลว (`docker ps` แสดงเวิร์กเกอร์เป็น `unhealthy`) หลังจาก 30 นาที กระดิ่งและการแจ้งเตือนจะบอกว่าเวิร์กเกอร์เข้าถึง Docker ไม่ได้ `docker logs cashpilot-socket-proxy` แสดง `upstream Docker socket unreachable` และหากใช้ไฟล์ compose ปัจจุบัน `docker ps` จะแสดง proxy เป็น `unhealthy` ภายในประมาณ 3 นาที แอปหารายได้ยังคงทำงานต่อ

**สาเหตุ** ไฟล์ compose ที่มาพร้อมกัน bind ไฟล์ socket `/var/run/docker.sock` เข้าไปใน `cashpilot-socket-proxy` การ bind ไฟล์จะยึดไฟล์นั้นไฟล์เดียว การอัปเดต Docker (เช่น `unattended-upgrades` ติดตั้ง `docker-ce` ใหม่) จะรีสตาร์ต Docker และ Docker จะสร้างไฟล์ socket ใหม่ที่พาธเดิม เมื่อเปิด live-restore ของ Docker ไว้ proxy จะทำงานต่อผ่านการรีสตาร์ตนั้นและยังยึดไฟล์เก่าไว้ ซึ่งไม่มีอะไรตอบกลับบนไฟล์เก่าแล้ว

**วิธีแก้ด่วน** บนเครื่องนั้น ให้รีสตาร์ต proxy:

```bash
docker restart cashpilot-socket-proxy
```

การรีสตาร์ตจะ bind socket ใหม่ และเวิร์กเกอร์จะพบ Docker อีกครั้งในสัญญาณชีพถัดไป ไม่ต้องรีสตาร์ตเวิร์กเกอร์ บน Unraid และ TrueNAS เวิร์กเกอร์ถือ socket เอง จึงให้รีสตาร์ตเวิร์กเกอร์แทน

**วิธีแก้ถาวร** ให้ bind โฟลเดอร์ของ socket ไม่ใช่ไฟล์ socket การ bind โฟลเดอร์จะเห็น socket ที่ถูกแทนที่ทันที ในบริการ `cashpilot-socket-proxy` ของไฟล์ compose ให้แทนบรรทัด `- /var/run/docker.sock:/var/run/docker.sock:ro` ด้วยการ bind ด้านล่าง และเพิ่มบรรทัด `SOCKGUARD_UPSTREAM_SOCKET` ลงใน `environment`:

```yaml
    volumes:
      - type: bind
        source: /var/run
        target: /host-run
        read_only: true
        bind:
          recursive: disabled
      - cashpilot_docker_api:/run/cashpilot-docker
    environment:
      # Keep the lines that are already there, and add this one:
      - SOCKGUARD_UPSTREAM_SOCKET=/host-run/docker.sock
```

จากนั้นรัน `docker compose up -d` การเปลี่ยนแปลงเดียวกันใช้ได้ใน `docker-compose.worker.yml` และ `docker-compose.fleet.yml` ด้วย Compose อ่านไฟล์เหล่านั้นเฉพาะเมื่อระบุชื่อ จึงต้องรัน `docker compose -f docker-compose.worker.yml up -d` หรือ `docker compose -f docker-compose.fleet.yml up -d` เว้นแต่ `COMPOSE_FILE` จะระบุไฟล์นั้นไว้อยู่แล้ว

- `recursive: disabled` จำเป็น `/var/run` มี mount อื่นอยู่ด้วย เช่น network namespace ของ Docker ใต้ `/run/docker/netns` และ `/run/user/...` การ bind แบบ recursive จะนำทั้งหมดเข้าไปใน proxy ส่วนการ bind แบบไม่ recursive จะแสดงเฉพาะตัวโฟลเดอร์เอง
- `SOCKGUARD_UPSTREAM_SOCKET` ชี้ proxy ไปยังพาธใหม่ บล็อกนโยบายและ fingerprint ของบล็อกยังคงเหมือนเดิม เพราะตัวแปรสภาพแวดล้อมนี้มีผลเหนือ `upstream.socket` ในนโยบาย หากไม่มีตัวแปรนี้ proxy จะไม่เริ่มทำงาน (`upstream socket not found (/var/run/docker.sock)`)
- `cashpilot-migrate` ใช้การ bind ไฟล์ต่อไปได้ เพราะเริ่มใหม่ทุกครั้งที่ `docker compose up` จึงได้ socket ปัจจุบันเสมอ หากให้การ bind โฟลเดอร์แบบเดียวกัน ให้เพิ่ม `DOCKER_HOST=unix:///host-run/docker.sock` ลงใน `environment` ของ `cashpilot-migrate` เวิร์กเกอร์ 2.8.4 ขึ้นไปอ่านตัวแปรนั้น อย่าชี้ไปที่ socket ของ proxy เด็ดขาด เพราะตัวย้ายข้อมูลต้องใช้ socket ของโฮสต์เอง
- การ bind โฟลเดอร์ให้ proxy เข้าถึงทุก socket ใน `/var/run` ไม่ใช่เฉพาะของ Docker บนเซิร์ฟเวอร์ทั่วไป ซึ่งรวมถึง socket ของ systemd เอง D-Bus และ socket ของเครื่องมืออย่าง Tailscale หรือ snapd `read_only` ไม่ได้ห้ามโปรแกรมเชื่อมต่อกับ socket และ proxy รันเป็น root การเข้าถึง Docker socket ให้สิทธิ์ root บนโฮสต์อยู่แล้ว proxy ที่ถูกเจาะจึงได้สิทธิ์เพิ่มเพียงเล็กน้อย หากต้องการให้ proxy ถือเฉพาะ Docker socket ให้ใช้การ bind ไฟล์ต่อไป และรีสตาร์ต proxy หลังอัปเดต Docker การแจ้งเตือนด้านบนจะบอกว่าเมื่อใด
- ต้องใช้ Docker Compose 2.30.0 ขึ้นไป รุ่นเก่ากว่าจะปฏิเสธทั้งไฟล์ด้วย `Additional property recursive is not allowed` รัน `docker compose version` เพื่อตรวจสอบ Debian 13 มีแพ็กเกจ Compose 2.26.1 ดังนั้นบน Debian ให้ติดตั้ง Compose จากที่เก็บของ Docker เอง การอัปเดตจากในแอปใช้ Compose 2.33 ของตัวเอง จึงอ่านไฟล์ที่เปลี่ยนแล้วได้
- ใช้ได้บน Linux เท่านั้น Docker Desktop บน macOS และ Windows แมปเฉพาะ `/var/run/docker.sock` เข้าไปในเครื่องเสมือน ที่นั่น `/var/run` เป็นโฟลเดอร์บน Mac หรือ PC ซึ่งไม่มี Docker socket อยู่
- สำหรับ Docker แบบ rootless นั้น socket อยู่ใน `/run/user/<your uid>` ซึ่งเป็น mount แยกต่างหาก ให้ใช้โฟลเดอร์นั้นเป็น `source`
- บน Podman ให้ใช้การ bind ไฟล์ต่อไป เรายังไม่ได้ทดสอบการ bind โฟลเดอร์ที่นั่น

ไฟล์ที่มาพร้อมกันยังใช้การ bind ไฟล์ เพราะการ bind โฟลเดอร์ต้องใช้ Compose 2.30 และ Linux ขณะที่ CashPilot ยังรองรับ Compose รุ่นเก่ากว่าและ Docker Desktop ด้วย ไฟล์ compose ที่ใหม่กว่าซึ่งดาวน์โหลดมาจะไม่มีการเปลี่ยนแปลงของคุณ จึงต้องแก้อีกครั้งหลังจากแทนที่ไฟล์

# Часті запитання { #faq }

**Чи безпечно ділитися трафіком?**

Сервіси поширення трафіку здебільшого пропускають через ваше з'єднання легітимний трафік (маркетингові дослідження, перевірка реклами, порівняння цін, доставка контенту). Водночас ви ділитеся своєю IP-адресою, тож уважно перегляньте умови користування й політику конфіденційності кожного сервісу, перш ніж реєструватися. Для деяких сервісів можна запускати їх на VPS замість домашньої IP. **Це не юридична консультація -- зверніться до конкретних сервісів, якими збираєтеся користуватися, і за потреби отримайте незалежну юридичну консультацію щодо вашої юрисдикції.**

**Скільки можна заробити?**

Заробіток дуже різниться залежно від місця, інтернет-провайдера, кількості пристроїв і того, які сервіси ви запускаєте. Панель відстежує ваш фактичний заробіток із часом, щоб ви могли оптимізувати своє налаштування. Як приблизний орієнтир, а не обіцянка: один домашній сервер із 10–15 сервісами приносить близько $30–$100 на місяць, а може й менше, аж до нуля. Більше серверів або обчислення на GPU додають до цього.

**Чи можна запускати на VPS або хмарному сервері?**

Деякі сервіси вимагають домашньої IP і не платитимуть за IP VPS/дата-центрів (або заблокують їх). Каталог вказує «домашня IP» серед того, що їм потрібно. Сервіси, які працюють на VPS, — гарний спосіб масштабуватися без додаткового домашнього обладнання.

**Як зберігаються облікові дані?**

Усі облікові дані сервісів зашифровано на диску в базі даних SQLite ключем Fernet, що зберігається в `/data/.fernet_key` і генерується автоматично під час першого запуску. Файл бази даних лежить у змонтованому томі Docker (`cashpilot_data:/data`). Облікові дані ніколи нікуди не надсилаються, крім самих контейнерів сервісів.

Зверніть увагу, що це інший ключ, ніж `CASHPILOT_SECRET_KEY`, який лише підписує сеанси входу.

### Резервне копіювання ключа шифрування { #backing-up-the-encryption-key }

Ваші облікові дані можна відновити лише доти, доки є `/data/.fernet_key`. Якщо ви втратите цей файл, доведеться заново ввести всі облікові дані, бо без нього розшифрувати збережені значення неможливо.

```bash
# Back it up
docker exec cashpilot-ui cat /data/.fernet_key

# Restore onto a fresh volume: pass the saved value when starting CashPilot.
# It must reach the container, so put it on the same command line (or export it,
# or set it in your .env) - a bare shell assignment on its own line does nothing.
CASHPILOT_ENCRYPTION_KEY=<the value you saved> docker compose up -d
```

Файл завжди має пріоритет над змінною середовища, тож задати `CASHPILOT_ENCRYPTION_KEY` на екземплярі, який уже має ключ, нічого не змінює і безпечно. Змінна застосовується лише тоді, коли файлу ключа немає, а це саме випадок відновлення.

Якщо CashPilot узагалі не може записати ключ на диск, бо `/data` недоступний для запису або не змонтований, він відмовляється запускатися, щоб не шифрувати ваші облікові дані ключем, який зникне під час наступного перезапуску. Задайте `CASHPILOT_ALLOW_EPHEMERAL_KEY=true`, якщо ви справді цього хочете.

### Забули пароль або ім'я користувача { #forgot-password-or-username }

У CashPilot немає скидання пароля через e-mail. Той, хто керує сервером, скидає пароль із консолі контейнера CashPilot UI. Ваші сервіси, заробіток і збережені облікові дані це не зачіпає: вони зашифровані ключем `/data/.fernet_key`, а не вашим паролем.

Команда `python -m app.users` потребує CashPilot 2.3 або новішого. На 2.2 і старіших вона завершується помилкою `No module named app.users`. Спершу оновіться: у Docker Compose змініть теги `drumsergio/cashpilot` і `drumsergio/cashpilot-worker` на `2.3` або новіші (закріплення на кшталт `2.2` чи `2.2.9` залишається на тому випуску), а потім виконайте `docker compose up -d` ([Оновлення CashPilot](getting-started.md#updating-cashpilot)). В Unraid оновіть контейнер.

1. Виведіть список акаунтів. Він також показує ім'я користувача, яке ви забули. Імена користувачів чутливі до регістру.

    ```bash
    docker exec -it cashpilot-ui python -m app.users list
    ```

2. Задайте акаунту новий випадковий пароль. Замініть `alice` на ім'я користувача з кроку 1.

    ```bash
    docker exec -it cashpilot-ui python -m app.users reset-password alice
    ```

    Якщо власник рівно один, ім'я користувача можна не вказувати, і команда скине пароль цього власника. Якщо ім'я користувача починається з `-`, поставте перед ним `--`: `reset-password -- -alice`.

    Команда один раз виводить новий пароль.

3. Якщо до акаунта міг мати доступ хтось інший, перезапустіть контейнер UI зараз (`docker restart cashpilot-ui`). Браузери, у яких досі виконано вхід як цей користувач, виходять із системи лише після перезапуску. Якщо ви просто забули пароль, перезапуск необов'язковий.
4. Увійдіть із новим паролем, а потім змініть його в меню аватара (угорі праворуч), **Change password** (Змінити пароль).

Ім'я контейнера залежить від того, як ви встановили CashPilot:

| Інсталяція | Контейнер UI |
|---|---|
| `docker-compose.yml`, CasaOS | `cashpilot-ui` |
| Unraid | `cashpilot` (`docker exec -it cashpilot python -m app.users list`) |
| Runtipi | згенероване ім'я; його показує `docker ps` |

Portainer, Unraid і CasaOS також мають для контейнера кнопку консолі. Команда не потребує введення в терміналі, тож працює і там.

Щоб змінити ім'я користувача:

```bash
docker exec -it cashpilot-ui python -m app.users rename OLD NEW
```

Нове ім'я підлягає правилу реєстрації: від 3 до 32 літер, цифр, `_` або `-`. Вийдіть і знову увійдіть, щоб його побачити.

**Після підозри на компрометацію**, наприклад коли загублено резервну копію з `/data/.secret_key`, одного скидання пароля недостатньо. Той, хто має цей ключ, може підписати дійсну cookie входу, і скидання цьому не завадить. Замініть ключ, а потім перезапустіть контейнер UI. `&&` перезапускає його лише тоді, коли новий ключ на місці; якщо команда виводить помилку, спершу виправте її:

```bash
docker exec cashpilot-ui python -m app.users rotate-session-key && docker restart cashpilot-ui
```

Після перезапуску всі браузери виходять із системи, і всі знову входять зі своїм паролем. Збережені облікові дані це не зачіпає. Якщо ви самі задали `CASHPILOT_SECRET_KEY`, команда відмовиться працювати: натомість запишіть у цю змінну нове випадкове значення і створіть контейнер заново. `docker run` з образу не бачить цієї змінної і не може відмовити, тож використовуйте `docker exec` для контейнера UI.

Новий ключ припиняє дію підроблених cookie, але не скасовує того, що зловмисник зробив, поки мав доступ. Ще два кроки:

1. Виконайте `docker exec cashpilot-ui python -m app.users list`. Видаліть на панелі будь-який акаунт, якого ви не впізнаєте.
2. Якщо втрачена копія містила весь `/data`, змініть паролі своїх акаунтів у провайдерів. `.fernet_key` і `cashpilot.db` разом розшифровують усі збережені облікові дані.

Якщо пізніше ви відновлюєте резервну копію, зроблену до заміни ключа, не відновлюйте її `.secret_key` ([Резервне копіювання та відновлення](backup-restore.md#restore)) або знову замініть ключ і перезапустіть. Інакше старий ключ повернеться. Відновлена база даних також повертає акаунти й паролі, які в ній були, тож повторіть перевірку акаунтів і всі скидання паролів.

**Якщо контейнер UI не запускається**, виконайте команду з того самого образу на тих самих даних. Спершу знайдіть теку хоста, яка містить `/data` UI. Це працює для зупиненого контейнера, а також для іменованого тому і для bind mount (Unraid, CasaOS, Runtipi):

```bash
docker inspect -f '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}' cashpilot-ui
```

Потім змонтуйте цю теку й використайте тег образу, який ви запускаєте:

```bash
docker run --rm -v "<folder>:/data" --entrypoint python drumsergio/cashpilot:<same tag> -m app.users list
```

Перевірте, що список показує ваші акаунти, а потім виконайте той самий рядок, поставивши `reset-password alice` замість `list`.

Шлях без бази даних дає помилку «no database», і команда нічого там не створює і не змінює. Docker однаково може залишити порожню теку чи том із цим іменем; видаліть їх.

**Не** видаляйте том даних: це знищить `/data/.fernet_key`, а разом із ним усі збережені облікові дані. **Не** видаляйте також рядки з таблиці `users`.

**Як повністю видалити CashPilot?**

`docker compose down -v` видаляє лише власні контейнери CashPilot. Розгорнуті ним сервіси продовжують працювати, а їхні дані, мережа за бар'єром і таблиця брандмауера залишаються. [Повне видалення CashPilot](uninstall.md) видаляє все це, пояснює, що буде втрачено назавжди, і показує, як перевірити, що нічого не залишилося.

**А як щодо безпеки?**

Кожен сервіс, який розгортає CashPilot, працює у власному контейнері з вимкненими всіма можливостями (capabilities) Linux (кілька сервісів повертають лише ті, які вони оголошують) і з параметром `--security-opt no-new-privileges`, тож процес усередині не може отримати привілеї. Контейнери не бачать файлової системи вашого хоста поза томами, які оголошує сервіс. На новій інсталяції воркер також відгороджує їх бар'єром від вашої LAN, хоста, вашого tailnet і хмарних метаданих, тож вони мають доступ до інтернету і ні до чого локального ([Ізоляція мережі](isolation.md)). У Podman бар'єр недоступний: застосунки для заробітку працюють у типовій мережі Podman, яка має доступ до вашої LAN, і сторінка **Fleet** (Парк) про це повідомляє ([Ізоляція мережі](isolation.md) перелічує варіанти). Інсталяція, оновлена з випуску, старішого за 1.70, тримає свої застосунки для заробітку на типовому bridge Docker, який має доступ до вашої LAN, доки ви не натиснете **Turn on isolation** (Увімкнути ізоляцію) на сторінці **Fleet** (Парк). Починаючи з 2.0.7 Mysterium теж працює за бар'єром; вузол, розгорнутий до 2.0.6 включно, залишається в мережі хоста, доки ви його не перерозгорнете ([Перенесення вузла Mysterium за бар'єр](mysterium-fence.md)). [Захист домашньої мережі](home-network-security.md) натомість описує налаштування брандмауера для власного bridge. Облікові дані сервісів зашифровано на диску симетричним шифруванням Fernet. UI не має доступу до Docker. З файлами compose, що постачаються, воркер ніколи не отримує «сирого» сокета Docker: він звертається до Docker через `cashpilot-socket-proxy`, який відхиляє привілейовані контейнери та прив'язки `/` або сокета (якщо ви не вказали одне з них або теку над сокетом у `CASHPILOT_PROXY_BIND_MOUNTS` чи `CASHPILOT_COMPOSE_DIR`: проксі приймає їх як є) і обмежує воркер контейнерами, томами та мережами з його міткою власника ([типові параметри безпеки](security-defaults.md)). Шаблони Unraid і застосунок TrueNAS досі монтують «сирий» сокет у воркер, а це root на хості ([магазини застосунків](app-stores.md)).

Утім, жодне налаштування не є бездоганним. Ви все одно запускаєте стороннє програмне забезпечення, яке пропускає зовнішній трафік через вашу мережу. Ізоляція Docker значно зменшує поверхню атаки порівняно із запуском цих сервісів безпосередньо на хості, але не усуває всіх ризиків. Радимо запускати CashPilot на окремій машині або у VLAN, оновлювати Docker і ОС хоста та переглядати відкритий код будь-якого сервісу перед його розгортанням.

**Що станеться, якщо контейнер сервісу впаде?**

CashPilot постійно стежить за працездатністю контейнерів. Якщо контейнер сервісу несподівано завершується, його автоматично перезапускають. Панель показує час роботи та стан працездатності кожного запущеного сервісу.

**Мій вузол Mysterium не запускається після перерозгортання. Чому?**

Найпоширеніша причина — порт у його діапазоні UDP, який уже зайняла інша програма на хості. Docker має зарезервувати кожен порт діапазону, тож один зайнятий порт зупиняє запуск. [Вибір діапазону портів UDP](mysterium-fence.md#choosing-the-udp-port-range) пояснює, як вибрати діапазон, що залишатиметься вільним.

**Моя копія через проксі працює, але нічого не заробляє. Чому?**

Проксі може відмовлятися з'єднуватися із серверами цього застосунку для заробітку або дозволяти лише порти 80 і 443. **Test** (Тест) у CashPilot перевіряє лише те, що проксі має доступ до інтернету. [Перевірте сервери застосунку для заробітку через проксі](proxies.md#probe-an-earners-servers-through-the-proxy) показує, як перевірити власний хост і порт застосунку для заробітку.

**Які сервіси важкі і де їх запускати?**

Найбільше ресурсів використовують вузли сховища, релеї та VPN-виходи, а також робота на GPU. [Бюджет для невеликої машини](fleet.md#budgeting-a-small-box) перелічує їх і показує, як виміряти кожен контейнер, перш ніж ухвалювати рішення.

<a id="worker-lost-docker"></a>

### Воркер утратив Docker після оновлення Docker { #the-worker-lost-docker-after-a-docker-update }

**Що ви бачите.** Воркер залишається онлайн на сторінці **Fleet** (Парк), але CashPilot не може запускати, зупиняти чи оновлювати його контейнери. Сторінка **Fleet** (Парк) показує поруч із воркером **Docker unreachable** (Docker недоступний). Через 10 хвилин перевірка працездатності воркера не проходить (`docker ps` показує воркер як `unhealthy`). Через 30 хвилин дзвіночок і ваші сповіщення повідомляють, що воркер не може дістатися до Docker. `docker logs cashpilot-socket-proxy` показує `upstream Docker socket unreachable`, а з поточним файлом compose `docker ps` показує проксі як `unhealthy` приблизно за 3 хвилини. Ваші застосунки для заробітку продовжують працювати.

**Причина.** Файли compose, що постачаються, прив'язують файл сокета `/var/run/docker.sock` у `cashpilot-socket-proxy`. Прив'язка файлу тримає саме цей один файл. Оновлення Docker (наприклад, `unattended-upgrades` встановлює новий `docker-ce`) перезапускає Docker, і Docker створює новий файл сокета за тим самим шляхом. Коли в Docker увімкнено live-restore, проксі продовжує працювати під час цього перезапуску і тримає старий файл. На старому файлі ніхто не відповідає.

**Швидке виправлення.** На цій машині перезапустіть проксі:

```bash
docker restart cashpilot-socket-proxy
```

Перезапуск прив'язує новий сокет, і воркер знову знаходить Docker під час наступного сигналу активності. Перезапускати воркер не потрібно. В Unraid і TrueNAS воркер сам тримає сокет, тому перезапустіть воркер.

**Постійне виправлення.** Прив'язуйте теку сокета, а не файл сокета. Прив'язка теки одразу показує замінений сокет. У сервісі `cashpilot-socket-proxy` вашого файлу compose замініть рядок `- /var/run/docker.sock:/var/run/docker.sock:ro` прив'язкою нижче і додайте рядок `SOCKGUARD_UPSTREAM_SOCKET` до його `environment`:

```yaml
    volumes:
      - type: bind
        source: /var/run
        target: /host-run
        read_only: true
        bind:
          recursive: disabled
      - cashpilot_docker_api:/run/cashpilot-docker
    environment:
      # Keep the lines that are already there, and add this one:
      - SOCKGUARD_UPSTREAM_SOCKET=/host-run/docker.sock
```

Потім виконайте `docker compose up -d`. Та сама зміна працює в `docker-compose.worker.yml` і `docker-compose.fleet.yml`. Compose читає ці файли, лише коли ви їх називаєте, тож виконайте `docker compose -f docker-compose.worker.yml up -d` або `docker compose -f docker-compose.fleet.yml up -d`, якщо `COMPOSE_FILE` ще не вказує цей файл.

- `recursive: disabled` обов'язковий. `/var/run` містить інші точки монтування, наприклад мережеві простори імен Docker у `/run/docker/netns` і `/run/user/...`. Рекурсивна прив'язка переносить їх усі в проксі. Нерекурсивна прив'язка показує лише саму теку.
- `SOCKGUARD_UPSTREAM_SOCKET` спрямовує проксі на новий шлях. Блок політики та його відбиток залишаються як є, бо змінна середовища перевизначає `upstream.socket` у політиці. Без цієї змінної проксі не запускається (`upstream socket not found (/var/run/docker.sock)`).
- `cashpilot-migrate` може залишити свою прив'язку файлу. Він знову запускається при кожному `docker compose up`, тож завжди отримує поточний сокет. Якщо ви дасте йому ту саму прив'язку теки, додайте `DOCKER_HOST=unix:///host-run/docker.sock` до його `environment`. Воркер 2.8.4 і новіші читають цю змінну. Ніколи не спрямовуйте її на сокет проксі: міграторові потрібен власний сокет хоста.
- Прив'язка теки дає проксі всі сокети в `/var/run`, а не лише сокет Docker. На типовому сервері серед них власний сокет systemd, D-Bus і сокети таких інструментів, як Tailscale чи snapd. `read_only` не заважає програмі під'єднатися до сокета, а проксі працює від root. Доступ до сокета Docker уже дає root на хості, тож скомпрометований проксі отримує мало такого, чого він не мав. Якщо ви хочете, щоб проксі тримав лише сокет Docker, залиште прив'язку файлу і перезапускайте проксі після оновлення Docker: сповіщення вище скаже вам, коли саме.
- Потрібен Docker Compose 2.30.0 або новіший. Старіші випуски відхиляють увесь файл із помилкою `Additional property recursive is not allowed`. Щоб перевірити, виконайте `docker compose version`. Debian 13 постачає Compose 2.26.1, тож у Debian встановіть Compose з власного репозиторію Docker. Оновлення із застосунку використовує власний Compose 2.33, тож воно читає змінений файл.
- Це працює лише в Linux. Docker Desktop на macOS і Windows відображає у свою віртуальну машину лише `/var/run/docker.sock`. Там `/var/run` — це тека на вашому Mac чи PC, у якій немає сокета Docker.
- У rootless Docker сокет лежить у `/run/user/<your uid>`, а це окрема точка монтування. Використайте цю теку як `source`.
- У Podman залиште прив'язку файлу. Ми не тестували там прив'язку теки.

Файли, що постачаються, зберігають прив'язку файлу, бо прив'язка теки потребує Compose 2.30 і Linux, а CashPilot також підтримує старіші випуски Compose і Docker Desktop. Новіший файл compose, який ви завантажите, не містить вашої зміни, тож внесіть її знову після заміни файлу.

# Вопросы и ответы { #faq }

**Безопасен ли обмен трафиком?**

Сервисы обмена трафиком обычно пропускают через ваше подключение законный трафик (маркетинговые исследования, проверка рекламы, сравнение цен, доставка контента). Тем не менее вы делитесь своим IP-адресом, поэтому перед регистрацией внимательно изучите условия использования и политику конфиденциальности каждого сервиса. Для некоторых сервисов можно запускать их на VPS, а не на домашнем IP. **Это не юридическая консультация: уточните условия у сервисов, которыми вы собираетесь пользоваться, и при необходимости обратитесь к независимому юристу, знакомому с законами вашей юрисдикции.**

**Сколько можно заработать?**

Заработок сильно зависит от местоположения, интернет-провайдера, числа устройств и того, какие сервисы вы запускаете. Панель отслеживает ваш реальный заработок со временем, чтобы вы могли оптимизировать свою установку. Для грубой ориентировки, а не как обещание: один домашний сервер с 10–15 сервисами приносит примерно $30–100 в месяц, а может приносить и меньше, вплоть до нуля. Больше серверов или вычисления на GPU добавляют к этому.

**Можно ли запускать на VPS или облачном сервере?**

Некоторым сервисам нужен домашний IP, и они не платят за IP VPS или дата-центров (или блокируют их). Каталог указывает «домашний IP» среди того, что им нужно. Сервисы, которые работают на VPS, — хороший способ расшириться без дополнительного оборудования дома.

**Как хранятся учётные данные?**

Все учётные данные сервисов хранятся в базе данных SQLite в зашифрованном виде ключом Fernet, который лежит в `/data/.fernet_key` и создаётся автоматически при первом запуске. Файл базы данных находится в подключённом томе Docker (`cashpilot_data:/data`). Учётные данные никогда никуда не отправляются, кроме самих контейнеров сервисов.

Обратите внимание: это другой ключ, не `CASHPILOT_SECRET_KEY`, который только подписывает сессии входа.

### Резервная копия ключа шифрования { #backing-up-the-encryption-key }

Ваши учётные данные можно восстановить ровно настолько, насколько можно восстановить `/data/.fernet_key`. Если вы потеряете этот файл, вам придётся заново вводить все учётные данные, потому что без него сохранённые значения расшифровать невозможно.

```bash
# Back it up
docker exec cashpilot-ui cat /data/.fernet_key

# Restore onto a fresh volume: pass the saved value when starting CashPilot.
# It must reach the container, so put it on the same command line (or export it,
# or set it in your .env) - a bare shell assignment on its own line does nothing.
CASHPILOT_ENCRYPTION_KEY=<the value you saved> docker compose up -d
```

Файл всегда имеет приоритет над переменной окружения, поэтому задать `CASHPILOT_ENCRYPTION_KEY` на экземпляре, у которого уже есть ключ, безопасно: это ничего не меняет. Переменная принимается, только когда файла ключа нет, а это как раз случай восстановления.

Если CashPilot вообще не может записать ключ на диск, потому что `/data` недоступен для записи или не смонтирован, он отказывается запускаться, а не шифрует ваши учётные данные ключом, который исчезнет при следующем перезапуске. Задайте `CASHPILOT_ALLOW_EPHEMERAL_KEY=true`, если вам действительно нужно именно это.

<a id="forgot-password"></a>

### Забыли пароль или имя пользователя { #forgot-password-or-username }

В CashPilot нет сброса по электронной почте. Пароль сбрасывает тот, кто управляет сервером, из консоли контейнера CashPilot UI. Ваши сервисы, заработок и сохранённые учётные данные это не затрагивает: они зашифрованы ключом `/data/.fernet_key`, а не вашим паролем.

Команде `python -m app.users` нужен CashPilot 2.3 или новее. На 2.2 и старше она падает с ошибкой `No module named app.users`. Сначала обновитесь: с Docker Compose измените теги `drumsergio/cashpilot` и `drumsergio/cashpilot-worker` на `2.3` или новее (закрепление вроде `2.2` или `2.2.9` остаётся на этом выпуске), затем выполните `docker compose up -d` ([Обновление CashPilot](getting-started.md#updating-cashpilot)). На Unraid обновите контейнер.

1. Выведите список аккаунтов. Так вы увидите и забытое имя пользователя. Имена пользователей чувствительны к регистру.

    ```bash
    docker exec -it cashpilot-ui python -m app.users list
    ```

2. Задайте аккаунту новый случайный пароль. Замените `alice` на имя пользователя из шага 1.

    ```bash
    docker exec -it cashpilot-ui python -m app.users reset-password alice
    ```

    Если владелец ровно один, имя пользователя можно не указывать, и команда сбросит пароль этого владельца. Если имя пользователя начинается с `-`, поставьте перед ним `--`: `reset-password -- -alice`.

    Команда один раз выводит новый пароль.

3. Если доступ к аккаунту мог быть у кого-то ещё, сразу перезапустите контейнер UI (`docker restart cashpilot-ui`). Браузеры, в которых ещё был выполнен вход под этим пользователем, выходят из аккаунта только после перезапуска. Если вы просто забыли пароль, перезапуск необязателен.
4. Войдите с новым паролем, затем смените его через меню аватара (справа вверху), **Change password** (Сменить пароль).

Имя контейнера зависит от того, как вы установили CashPilot:

| Установка | Контейнер UI |
|---|---|
| `docker-compose.yml`, CasaOS | `cashpilot-ui` |
| Unraid | `cashpilot` (`docker exec -it cashpilot python -m app.users list`) |
| Runtipi | сгенерированное имя; его показывает `docker ps` |

В Portainer, Unraid и CasaOS также есть кнопка консоли для контейнера. Команде не нужен ввод в терминале, поэтому она работает и там.

Чтобы изменить имя пользователя:

```bash
docker exec -it cashpilot-ui python -m app.users rename OLD NEW
```

Новое имя подчиняется правилу регистрации: от 3 до 32 букв, цифр, `_` или `-`. Выйдите и войдите снова, чтобы его увидеть.

**После подозрения на взлом**, например при потере резервной копии, в которой есть `/data/.secret_key`, одного сброса пароля недостаточно. Тот, у кого есть этот ключ, может подписать действительную cookie входа, и сброс этому не мешает. Замените ключ, затем перезапустите контейнер UI. `&&` перезапускает его, только когда новый ключ на месте; если команда выводит ошибку, сначала исправьте её:

```bash
docker exec cashpilot-ui python -m app.users rotate-session-key && docker restart cashpilot-ui
```

После перезапуска все браузеры выходят из аккаунтов, и все входят заново со своим паролем. Сохранённые учётные данные это не затрагивает. Если вы задали `CASHPILOT_SECRET_KEY` сами, команда откажется работать: вместо этого запишите в эту переменную новое случайное значение и пересоздайте контейнер. `docker run` из образа не видит эту переменную и не может отказаться, поэтому используйте `docker exec` в контейнере UI.

Новый ключ прекращает действие поддельных cookie, но не отменяет того, что злоумышленник сделал, пока был внутри. Ещё два шага:

1. Выполните `docker exec cashpilot-ui python -m app.users list`. Удалите в панели все аккаунты, которых вы не узнаёте.
2. Если в потерянной копии был весь `/data`, смените пароли своих аккаунтов у провайдеров. `.fernet_key` и `cashpilot.db` вместе расшифровывают все сохранённые учётные данные.

Если позже вы восстановите резервную копию, сделанную до замены ключа, не восстанавливайте её `.secret_key` ([Резервное копирование и восстановление](backup-restore.md#restore)) или снова замените ключ и перезапустите. Иначе старый ключ вернётся. Восстановленная база данных также возвращает аккаунты и пароли, которые в ней были, поэтому повторите проверку аккаунтов и, если нужно, сброс паролей.

**Если контейнер UI не запускается**, выполните команду из того же образа на тех же данных. Сначала найдите папку хоста, в которой лежит `/data` UI. Это работает для остановленного контейнера, и для именованного тома, и для bind mount (Unraid, CasaOS, Runtipi):

```bash
docker inspect -f '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Source}}{{end}}{{end}}' cashpilot-ui
```

Затем смонтируйте эту папку и используйте тег образа, который вы запускаете:

```bash
docker run --rm -v "<folder>:/data" --entrypoint python drumsergio/cashpilot:<same tag> -m app.users list
```

Убедитесь, что в списке ваши аккаунты, затем выполните ту же строку с `reset-password alice` вместо `list`.

Путь без базы данных даёт ошибку «no database», и команда ничего там не создаёт и не меняет. Docker всё же может оставить пустую папку или том с таким именем; удалите их.

**Не** удаляйте том с данными: это стирает `/data/.fernet_key`, а вместе с ним все сохранённые учётные данные. **Не** удаляйте и строки из таблицы `users`.

**Как полностью удалить CashPilot?**

`docker compose down -v` удаляет только собственные контейнеры CashPilot. Развёрнутые им сервисы продолжают работать, а их данные, огороженная сеть и таблица брандмауэра остаются. [Полное удаление CashPilot](uninstall.md) удаляет всё это, объясняет, что теряется безвозвратно, и показывает, как убедиться, что ничего не осталось.

**А что с безопасностью?**

Каждый сервис, который разворачивает CashPilot, работает в собственном контейнере, у которого отброшены все возможности (capabilities) Linux (несколько сервисов возвращают только те, которые они объявляют), и задан `--security-opt no-new-privileges`, поэтому процесс внутри не может получить дополнительные привилегии. Контейнеры не видят файловую систему хоста за пределами томов, которые объявляет сервис. На новой установке воркер также отгораживает их барьером от вашей LAN, хоста, вашей tailnet и облачных метаданных, поэтому они выходят в интернет и не видят ничего локального ([Изоляция сети](isolation.md)). На Podman барьер недоступен: приложения для заработка работают в сети Podman по умолчанию, из которой видна ваша LAN, и страница **Fleet** (Парк) сообщает об этом ([Изоляция сети](isolation.md) перечисляет варианты). Установка, обновлённая с выпуска до 1.70, держит свои приложения для заработка на мосте Docker по умолчанию, из которого видна ваша LAN, пока вы не нажмёте **Turn on isolation** (Включить изоляцию) на странице **Fleet** (Парк). Начиная с 2.0.7 Mysterium тоже работает за барьером; узел, развёрнутый в версиях до 2.0.6 включительно, остаётся в сети хоста, пока вы его не переразвернёте ([Перенос узла Mysterium за барьер](mysterium-fence.md)). Вместо этого [Защита домашней сети](home-network-security.md) описывает, как закрыть брандмауэром собственный мост. Учётные данные сервисов хранятся зашифрованными симметричным шифрованием Fernet. У UI нет доступа к Docker. С поставляемыми файлами compose воркер никогда не получает сам сокет Docker: он обращается к Docker через `cashpilot-socket-proxy`, который отклоняет привилегированные контейнеры и привязки `/` или сокета (если только вы не укажете одно из них или папку выше сокета в `CASHPILOT_PROXY_BIND_MOUNTS` или `CASHPILOT_COMPOSE_DIR`: их прокси принимает как есть) и ограничивает воркер контейнерами, томами и сетями с его меткой владельца ([безопасные настройки по умолчанию](security-defaults.md)). Шаблоны Unraid и приложение TrueNAS по-прежнему монтируют сам сокет в воркер, а это root на хосте ([магазины приложений](app-stores.md)).

Тем не менее ни одна установка не бывает неуязвимой. Вы всё равно запускаете стороннее ПО, которое пропускает внешний трафик через вашу сеть. Изоляция Docker заметно сокращает поверхность атаки по сравнению с запуском этих сервисов прямо на хосте, но не устраняет все риски. Мы рекомендуем запускать CashPilot на отдельной машине или в отдельной VLAN, своевременно обновлять Docker и ОС хоста и изучать открытый код любого сервиса перед его развёртыванием.

**Что происходит, если контейнер сервиса падает?**

CashPilot постоянно следит за работоспособностью контейнеров. Если контейнер сервиса неожиданно завершается, он автоматически перезапускается. Панель показывает время работы и состояние работоспособности каждого запущенного сервиса.

**Мой узел Mysterium не запускается после переразвёртывания. Почему?**

Самая частая причина — порт из его диапазона UDP, который уже занят другой программой на хосте. Docker должен зарезервировать каждый порт диапазона, поэтому один занятый порт не даёт запуститься. [Выбор диапазона портов UDP](mysterium-fence.md#choosing-the-udp-port-range) объясняет, как выбрать диапазон, который останется свободным.

**Моя копия через прокси работает, но ничего не зарабатывает. Почему?**

Прокси может отказываться подключаться к серверам этого приложения для заработка или пропускать только порты 80 и 443. **Test** (Проверить) в CashPilot проверяет только то, что прокси выходит в интернет. [Проверьте серверы приложения для заработка через прокси](proxies.md#probe-an-earners-servers-through-the-proxy) показывает, как проверить собственный хост и порт приложения для заработка.

**Какие сервисы тяжёлые и где их запускать?**

Больше всего ресурсов потребляют узлы хранения, релеи и выходные узлы VPN, а также задачи на GPU. [Бюджет небольшой машины](fleet.md#budgeting-a-small-box) перечисляет их и показывает, как измерить каждый контейнер, прежде чем решать.

<a id="worker-lost-docker"></a>

### Воркер потерял Docker после обновления Docker { #the-worker-lost-docker-after-a-docker-update }

**Что вы видите.** Воркер остаётся в сети на странице **Fleet** (Парк), но CashPilot не может запускать, останавливать или обновлять его контейнеры. Страница **Fleet** (Парк) показывает рядом с воркером **Docker unreachable** (Docker недоступен). Через 10 минут проверка работоспособности воркера не проходит (`docker ps` показывает воркер как `unhealthy`). Через 30 минут колокольчик и ваши уведомления сообщают, что воркер не может достучаться до Docker. `docker logs cashpilot-socket-proxy` показывает `upstream Docker socket unreachable`, а с текущим файлом compose `docker ps` примерно через 3 минуты показывает прокси как `unhealthy`. Ваши приложения для заработка продолжают работать.

**Причина.** Поставляемые файлы compose привязывают файл сокета `/var/run/docker.sock` к `cashpilot-socket-proxy`. Привязка файла держит именно этот файл. Обновление Docker (например, `unattended-upgrades` ставит новый `docker-ce`) перезапускает Docker, и Docker создаёт новый файл сокета по тому же пути. При включённом live-restore в Docker прокси продолжает работать во время этого перезапуска и держит старый файл. На старом файле никто не отвечает.

**Быстрое исправление.** На этой машине перезапустите прокси:

```bash
docker restart cashpilot-socket-proxy
```

Перезапуск привязывает новый сокет, и воркер снова находит Docker при следующем сигнале активности. Перезапускать воркер не нужно. На Unraid и TrueNAS воркер держит сокет сам, поэтому перезапустите воркер.

**Постоянное исправление.** Привяжите папку сокета, а не файл сокета. Привязка папки сразу показывает заменённый сокет. В сервисе `cashpilot-socket-proxy` вашего файла compose замените строку `- /var/run/docker.sock:/var/run/docker.sock:ro` на привязку ниже и добавьте строку `SOCKGUARD_UPSTREAM_SOCKET` в его `environment`:

```yaml
    volumes:
      - type: bind
        source: /var/run
        target: /host-run
        read_only: true
        bind:
          recursive: disabled
      - cashpilot_docker_api:/run/cashpilot-docker
    environment:
      # Keep the lines that are already there, and add this one:
      - SOCKGUARD_UPSTREAM_SOCKET=/host-run/docker.sock
```

Затем выполните `docker compose up -d`. То же изменение работает в `docker-compose.worker.yml` и `docker-compose.fleet.yml`. Compose читает эти файлы, только когда вы их называете, поэтому выполните `docker compose -f docker-compose.worker.yml up -d` или `docker compose -f docker-compose.fleet.yml up -d`, если только `COMPOSE_FILE` уже не указывает этот файл.

- `recursive: disabled` обязателен. В `/var/run` есть другие точки монтирования, например сетевые пространства имён Docker в `/run/docker/netns` и `/run/user/...`. Рекурсивная привязка приносит их все в прокси. Нерекурсивная привязка показывает только саму папку.
- `SOCKGUARD_UPSTREAM_SOCKET` направляет прокси на новый путь. Блок политики и его отпечаток остаются как есть, потому что переменная окружения переопределяет `upstream.socket` в политике. Без этой переменной прокси не запускается (`upstream socket not found (/var/run/docker.sock)`).
- `cashpilot-migrate` может оставить привязку файла. Он запускается заново при каждом `docker compose up`, поэтому всегда получает текущий сокет. Если вы дадите ему ту же привязку папки, добавьте `DOCKER_HOST=unix:///host-run/docker.sock` в его `environment`. Воркер 2.8.4 и новее читает эту переменную. Никогда не направляйте её на сокет прокси: мигратору нужен собственный сокет хоста.
- Привязка папки даёт прокси все сокеты в `/var/run`, а не только сокет Docker. На типичном сервере это сокет самого systemd, D-Bus и сокеты таких инструментов, как Tailscale или snapd. `read_only` не мешает программе подключиться к сокету, а прокси работает от root. Доступ к сокету Docker и так даёт root на хосте, поэтому взломанный прокси получает немногим больше, чем у него уже было. Если вы хотите, чтобы прокси держал только сокет Docker, оставьте привязку файла и перезапускайте прокси после обновления Docker: оповещение выше сообщит, когда это нужно.
- Нужен Docker Compose 2.30.0 или новее. Более старые выпуски отвергают весь файл с ошибкой `Additional property recursive is not allowed`. Проверьте командой `docker compose version`. В Debian 13 пакет Compose версии 2.26.1, поэтому в Debian устанавливайте Compose из собственного репозитория Docker. Обновление из приложения использует собственный Compose 2.33, поэтому читает изменённый файл.
- Это работает только в Linux. Docker Desktop на macOS и Windows передаёт в свою виртуальную машину только `/var/run/docker.sock`. Там `/var/run` — это папка на вашем Mac или ПК, в которой нет сокета Docker.
- В rootless Docker сокет находится в `/run/user/<your uid>`, а это отдельная точка монтирования. Используйте эту папку как `source`.
- На Podman оставьте привязку файла. Привязку папки там мы не тестировали.

Поставляемые файлы оставляют привязку файла, потому что привязке папки нужны Compose 2.30 и Linux, а CashPilot поддерживает и более старые выпуски Compose, и Docker Desktop. В новом файле compose, который вы скачаете, вашего изменения нет, поэтому внесите его снова после замены файла.
